## 1. 缺陷与根因

| 编号 | 现象（用户可见） | 根因 | 证据 |
| --- | --- | --- | --- |
| BUG-07 | 选中附件块后，布局浮条出现在上方图片块上，与附件卡片无关 | 浮条 `left:50%` 相对 `.attachment-block-shell` 居中，而该外壳是普通块元素、宽度等于整行正文宽度；卡片本身只有 210px 且靠左。图片块不受影响，因为其外壳在 flex 容器里会收缩到图片宽度 | 修复前实测：单卡片正文列宽 720px 时浮条中心 750（列中心），卡片中心 105 |
| BUG-08 | 从访达把文件拖进窗口后没有任何反应，既不上传也不插入 | `tauri.conf.json` 未设置 `dragDropEnabled`，其默认值为 true：框架在原生层接管拖放，网页收不到 HTML5 `drop`，`@tiptap/extension-file-handler` 的 `onDrop` 因此从不触发 | Tauri 官方配置文档原文：“By default it is enabled. Disabling it is required to use HTML5 drag and drop on the frontend”；与早前官方 DragHandle 在 WKWebView 失效的成因一致 |

## 2. 修复方案

- BUG-07：把对齐交给 `.attachment-block`（flex + `justify-content`），卡片形态下让 `.attachment-block-shell` 以 `width: fit-content` 收缩到卡片组宽度，长条形态仍铺满正文宽度；浮条继续居中于外壳，于是居中点即附件组中心。
- BUG-08：新增 `src/api/dragDrop.ts` 订阅 `getCurrentWebview().onDragDropEvent`，只处理 `drop`；事件坐标是相对 webview 左上角的物理像素，按 `devicePixelRatio` 换算为视口 CSS 像素。落点经 `resolveDropInsertPos` 解析后，走既有的**路径流式上传**（`uploadPathsAndInsert`，`kind: "auto"`），图片插入图片块、其余合并为一个附件块。
- 落点判据：落点在正文容器（`.doc-editor-body`）之外 → 返回 `null`，本次拖放直接放弃，不写入文档；在容器内但命中不到文字位置 → 退回文档末尾。

## 4. 视觉证据

修复后单卡片场景（图片块在上、附件卡片在下、浮条贴在卡片组正中）已用 Chrome 实际渲染截图核对：浮条不再压在图片块右下角，横向中心与卡片一致；浮条底边与图片块底边仍有约 22px 重叠，属于浮层跨在上一块之上的常规表现（`z-index: 8` + 阴影 + 背景模糊）。

截图未能落盘：Chrome DevTools MCP 的 `filePath` 受其自身 workspace root 限制，写入本仓库目录被拒（`Access denied ... not within any of the configured workspace roots`），本轮以对话内联截图 + 上表几何读数为准。
