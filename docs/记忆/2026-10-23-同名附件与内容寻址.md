# 记忆：同名附件与内容寻址（2026-10-23）

## 结论先说

内容寻址存储里，**文件名不是身份**。附件身份是 `id`，去重靠 BLAKE3，物理路径由哈希决定。一旦给 `(目录, 文件名)` 加唯一约束，就等于把展示层的偶然重复当成数据层冲突——两张不同的截图都叫 `image.png` 是常态，用户看到的是"传不上去"。

## 这次是怎么错的

任务-005 设计对象存储时，"活跃路径唯一"是从网盘/文件系统的直觉里带进来的默认设定，需求文档、迁移、服务层预检、错误翻译四处各写了一遍。四份实现互相强化，看起来像一条被反复确认过的规则，其实没有任何一条来自真实需求。真机第一次连续粘贴同名剪贴板图片就把它撞穿了。

- 撤销时要一次撤干净：DB 索引、两处服务预检、把约束冲突翻译成人话的 `map_attachment_insert_error`、以及失去调用方的 `find_active_by_path`。只删预检不删索引，SQLite 还会抛约束冲突；只删索引不删预检，规则仍在，只是换了个报错来源。
- 也不要留"半条规则"：只放开上传、保留改名重名冲突，等于同一条业务含义两处口径不一致。

## 判据怎么才不算自证

- **先复现再改**：新用例在改前运行，报错文本必须与用户截图逐字一致（`该目录下已存在同名附件`）。这一步能证明修的是同一条规则，而不是顺手改绿了一个不相干的断言。
- **删约束的测试要证明约束真的没了**：光断言"索引名不在列表里"仍然可能是别处兜住的。补一条最直接的：在迁移后的库上直插两条同目录同名活跃行，插入必须成功。
- **断言翻正要看方向**：`attachment_rename_and_move_only_change_metadata` 里原来写着「目标路径重名必须冲突」。这类"旧规则的反面断言"最容易被顺手删掉——删了就等于没留证据。改成断言同名上传成功且 id 不同，规则变更才在测试里留下痕迹。
- 去重与计数分开看：`unique_objects` 只数物理对象，`active_count` 数逻辑行。同名同内容时两者一个不变一个增长，正好证明"允许重名"没有把去重搞坏。

## 迁移落点

- `SCHEMA_VERSION` 5 → 6；`MIGRATION_V5_TO_V6` 只做 `DROP INDEX` + 建非唯一索引，不动数据。
- 历史迁移 `MIGRATION_V4_TO_V5` 原样保留（含它建的唯一索引），由 v6 负责撤下；空库按 v4→v5→v6 连跑，终态一致。改写已发布的迁移会让"老库升级"和"新库初始化"走出两条不同的路，是更难查的坑。
- 迁移测试里的版本断言写死字面量 6，不写 `SCHEMA_VERSION`——否则常量本身错了测试照样绿。

## 前端侧顺带确认

- 编辑器附件项 key 用 `item.uid ?? item.attachmentId`，设置页列表 key 用 `item.id`，都不依赖文件名唯一，所以这次前端零改动。
- 之前踩过的一类坑在这里同样成立：延迟/异步写要带来源身份（`docSeqRef`），上传批次插入前判断文档是否已切换。

## 第 2 轮：口径来回了一次，最终固化的是引用计数

先按"命中同哈希就返回已有 id"实现了一版（`find_active_by_hash` + `upload_staged` 早退），随后口径更正为：**同一文件重复上传（文件名可以不一样）= 多条记录、多个 id，但真实文件只有一份；每个对象带引用计数，引用全部消失才可删除** —— 也就是回退到原实现。早退与 `find_active_by_hash` 都已删除，不留死代码。

留下三件事：

- **这套语义本来就在，缺的是"别再去优化它"**。回退时在 `upload_staged` 函数头写了模型说明并标注"勿改成命中即复用 id"。判据是：一条规则如果每次核对都有人想改它，说明它没被写下来，只活在代码形状里。
- **引用计数要能被测试钉住**。"删到只剩一条时文件仍在、删最后一条才消失"必须逐条断言到真实文件系统（`big_path.is_file()` / `!big_path.exists()`）与 `ref_count`、`unique_objects`、`physical_bytes` 三个读数上；只断言"两次上传都成功"证明不了去重，也证明不了引用计数。
- **`ref_count` 数的是逻辑记录数，不是文档节点引用数**。所以"引用全部消失"目前只覆盖"所有附件记录都删了"；在设置页删一条仍被文档引用的附件，节点会显示损坏态。这不是本轮遗漏，是文档侧从来没登记过引用，要真安全得补「文档节点 → 附件」登记，属另一个需求。

### 暂存文件按哈希命名的先后顺序

`tmp/<hash>.part` 这个名字**写完才知道**，所以只能两段式：写入期用唯一临时名，算完哈希再 rename。直接以哈希名打开文件写是做不到的（除非先整读一遍算哈希，那会让"新文件"这条最常见的路径多读一整遍）。

- 并发的正确性靠一条不变量兜住：**`tmp/<hash>.part` 里的字节必然等于 `<hash>`**。所以两个线程撞名时，后到的删掉自己那份直接采用既有路径，谁去 rename 谁发布都不会写错内容。
- 改名后如果命中去重，那份文件由 `cleanup_staged` 删；若已被先行的发布者 rename 走了，删除时 NotFound 属正常，`cleanup_staged` 一直容忍它。
- 顺带纠正一个说法：磁盘上此前**也没有**出现过用户真实文件名（big 用哈希名、pack 用 pack id、临时文件用 uuid）。改成哈希名带来的是"崩溃残留自描述"，不是"首次不泄露文件名"。写文档时别把前者说成后者。

### 改口径要连带的观感检查

同一个 `attachmentId` 可以在一个附件块里出现两次（复制/拖动块会连带复制 items），于是"下载忙碌态按 attachmentId 记"这种看似无关的写法会露馅：两颗按钮一起转圈。凡是"按 id 记 UI 状态"的地方，都要在 id 可能重复时重看一遍，判据复用 React key 那一份（`uid ?? attachmentId`），别再抄第二份身份。

## 第 3 轮：删掉 ref_count

`attachment_blob.ref_count` 是冗余状态：物理对象该不该留，只看"还有没有活跃 `attachment` 行引用这个哈希"，一条走 `idx_attachment_hash` 的 COUNT 就够。存一列维护它 = 给同一个事实留第二份真相，写入路径漏一次就永久漂移，读的时候还得相信它。已删（v7）。

### 判断"冗余"与顺带的简化

- 删掉计数器后，pack 侧 5 处 `ref_count > 0` 过滤全都可以去掉：**blob 行只在被引用期间存在**本身就是不变量（创建必伴随一条逻辑记录，归零即删行）。于是 `max_indexed_end` / `live_bytes_in_pack` / `list_live_blobs_in_pack` / `move_blob_to_pack` / 统计子查询一起变简单——这是"删冗余"最常见的红利：一个字段消失，围绕它的防御性过滤也跟着失去意义。
- 反向检查：删之前先确认没有第二条写入路径需要它（这里只有上传与删除两处，且都在同一事务）。若有多条写入路径，先收口再删，否则会删出一个更隐蔽的缺失。

### SQLite 的 DROP COLUMN 陷阱

`ref_count INTEGER NOT NULL DEFAULT 0 CHECK (ref_count >= 0)` 这种**列级 CHECK** 会让 `ALTER TABLE ... DROP COLUMN` 直接失败——SQLite 只允许删"未被任何索引/约束/外键/生成列引用"的列。正确做法是官方那套重建：建新表 → `INSERT ... SELECT` → `DROP TABLE` → `RENAME` → 重建索引。重建后别忘了**手动补回索引**：`DROP TABLE` 会连带删掉旧表的索引，这一步漏了不会报错，只会在下次查询时变慢。

### 迁移测试要带数据

只测"新库没有这一列"是自证——空表重建永远成功。真正会坏的是搬运那一步，所以夹具里要先塞一条 v6 形状的 blob 行（带 `ref_count=3`）和一条附件行，升完再断言：列消失、`size/kind/pack_id/offset` 原样、索引补回、引用数按活跃附件重算为 1。历史值 3 与重算值 1 不一致，正好证明"不再读计数器"。

### 删除守卫必须有牙

把 `if remaining == 0` 临时改成 `>= 0`（无条件删对象），去重用例要能立刻红在 `!deleted_first.physical_deleted`。这一步花不到一分钟，但它能证明"引用归零才删"这条结论不是靠测试自我确认。
