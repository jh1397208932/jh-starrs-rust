## 1. 结论速览（TL;DR）

1. **不建议引入 GSAP，结论与 2026-10-20 的 001/002 报告一致，本次复核没有出现翻案证据。** GSAP 不能解决当前的主要瓶颈；它还会引入第二套动画体系，并且过不了项目的许可证门禁（详见 §7）。
2. **当前问题不是"动画引擎不够强"，而是"每帧要做的事情太多"**。主要成本集中在五处：
   - 大面积实时 `backdrop-filter`（全屏弹窗遮罩 + 弹窗本体 + 通高信息浮窗 + 导图面板）在动画/移动时反复重算模糊；
   - 弹窗/Toast/搜索等 UI 状态挂在 `WorkspaceRoot`，没有渲染边界，打开弹窗会连带重渲染整个侧栏、编辑器/画板/导图；
   - 标签切换用 `AnimatePresence mode="wait"` 先退场再挂载重型编辑器，挂载工作与入场动画抢同一帧；
   - 鼠标/拖拽热路径上存在 O(块数)/O(树节点数) 的 `getBoundingClientRect` 扫描与逐事件 `setState`；
   - 侧栏折叠是"宽度瞬切 + 内容滑出"，主编辑区在滑动开始的一帧内整体重排。
3. **现有动画实现方向本身是对的**：CSS 只动 `transform/opacity`，Motion 只做弹簧与进出场，没有 layout 动画、没有逐帧写 DOM 的循环。把 CSS 换成 GSAP 不会让这些路径更快。
4. **必须先在正确的构建档位上复测**。审计期间检测到的运行实例是 `target/debug` + Vite dev（e2e 调试实例，React 开发构建 + StrictMode），这个档位不能用来判定 60/120fps；应使用生产前端构建（`tauri build --debug` 带 devtools，或 release 包）复测。
5. **120fps 的预算只有 8.3ms/帧**。以当前的大面积模糊 + 整树重渲染 + 重型视图重挂载组合，不可能稳定 120fps；即使优化后，也应把"120fps"限定在纯 transform/opacity 的小面积动效上，而不是所有弹窗/面板。
6. **建议顺序**：P0 先做构建档位校正 + 真机帧采样 + 运行时 A/B（关模糊/关动画对比）；P1 再按"合成成本 → 渲染边界 → 视图挂载 → 指针热路径 → 布局结构"逐项治理；P2 处理打字期草稿写入、字数统计、导图/画板大对象等次要成本。

## 4. 每帧预算与测量口径

### 4.1 预算

- 60Hz：16.7ms/帧；120Hz：8.33ms/帧。
- 当前动效时长 140-300ms：在 120Hz 下是 17-36 帧。
- 一帧内同时发生：React 提交（JS）→ 样式/布局（主线程）→ 绘制/合成（GPU/合成线程）。任一环节超预算就会掉帧。
- `backdrop-filter` 不是"免费的 GPU 效果"：它需要对背景做采样/模糊；当承载它的层在移动或透明度变化时，模糊结果需要逐帧重算。全屏遮罩 + 弹窗本体双层模糊是最坏组合之一。

### 4.2 本轮为什么没有给 FPS 数字

- 当前实例是 debug + Vite dev，不能代表生产性能；
- Tauri 的 WKWebView 不能像 Chrome 一样被本机 Chrome DevTools 直接 attach；本轮没有可用的自动化 WKWebView 帧采样通道；
- 在不改代码的前提下，最可靠的读数是 Safari Web Inspector 的 Timeline/FPS 面板 + 页面内 rAF 采样，需要人工在真机窗口上操作。

因此本报告只给"机制定位 + 测量方案"，不给未经测量的 FPS 数字。这符合项目"不得伪造性能结果"的约束。

## 5. 瓶颈清单（按预期影响排序）

> 以下"影响"均为机制推断（D 级），需按 §9 在真机上验证。

### B1. 大面积实时模糊层在动画中被逐帧重算（最可疑）

**机制**：`backdrop-filter` 需要对下方内容做模糊采样。层一旦移动（`translate`）或透明度变化，合成器必须重新计算模糊；模糊半径越大、面积越大、层数越多，成本越高。全屏遮罩 + 弹窗本体双层模糊属于最坏组合。

**代码事实**：

- 弹窗遮罩：全屏 `bg-foreground/25 backdrop-blur-md`，同时用 `anim-fade-in` 做透明度入场 —— `src/components/ui/dialog.tsx:25`；
- 弹窗本体：`bg-popover/92 ... shadow-lg backdrop-blur-2xl` —— `src/components/ui/dialog.tsx:75`；
- 信息浮窗：通高（`top-16 bottom-5`）264px 面板 `bg-card/80 shadow-lg backdrop-blur-2xl`，外层用 Motion 弹簧做 `x/opacity` 入场 —— `src/features/workspace/components/InfoFloat.tsx:27-37`；
- 导图：底部工具栏、右侧检查器、搜索、悬浮卡、大纲面板均为 14-16px 模糊 —— `src/features/mindmap/mindmap.css:263/287/359/557/924`；
- 画板：`backdrop-filter: blur(10px)` —— `src/features/board/board.css:78`；
- 编辑器浮层：拖拽 chip、浮动菜单、气泡菜单、附件工具条 12-22px 模糊 —— `src/styles/app.css:910/949/1034/1328`；
- Toast、下拉菜单、引导卡、窗口栏激活标签等 Tailwind 模糊类共 10 处（如 `AppToast.tsx:27`、`dropdown-menu.tsx:21`、`WorkspaceOnboarding.tsx:68`、`WindowBar.tsx:75/127`）。

**为什么它最可疑**：

- 弹窗/浮窗的"不丝滑"与"模糊"在时间上完全重合；
- 信息浮窗在内容滚动时是固定覆盖层，下方内容滚动会持续触发其背景重采样；
- 全屏遮罩在淡入的 300ms 内，模糊层本身在改变透明度，等于要求每帧重算全屏模糊。

**验证方法**：在真机 Web Inspector 里临时注入 `*{backdrop-filter:none!important}`，对比同一弹窗/浮窗的 Timeline 与 rAF 直方图；不需要改代码。

### B2. 全应用重渲染：弹窗/Toast/自动保存都会牵动整棵树

**机制**：`dialog`、`toast` 状态在 `WorkspaceRoot`；`WorkspaceMain` 每次渲染都会重新执行 `useWorkspaceMainController`，而 `WorkspaceLayout`、`TabContentView`、`DocEditor`、`BoardView`、`MindmapView`、`Sidebar` 都没有 `memo` 边界。任何顶层状态变化都会让整棵树重新执行 render。

**代码事实**：

- `WorkspaceRoot` 持有 `toast` 与 `dialog` 状态 —— `src/features/workspace/components/WorkspaceRoot.tsx:20-21`；
- `WorkspaceMain` 只做组合，没有 memo —— `src/features/workspace/components/WorkspaceMain.tsx:15-20`；
- `WorkspaceLayout` 直接接收 controller，没有渲染隔离 —— `src/features/workspace/components/WorkspaceLayout.tsx:18-56`；
- 文档保存成功后 `applyDocumentSaved` 用 `nodesRef.current.map` 生成新节点数组并 `applyNodes` —— `src/features/workspace/hooks/useWorkspaceStore.ts:314-321`；
- `applyNodes` 每次都 `setNodes` + `setTree(buildTree(next))` —— 同文件 `:84-88`；
- `store.nodes` 变化触发 `syncTabs`，而 `syncTabs` 每次都 `map` 出新 tab 对象 —— `src/features/workspace/hooks/useTabSession.ts:59-75`；
- `InfoPanel` 在 `node.updatedAt` 变化时重新请求知识网络 —— `src/features/workspace/components/InfoPanel.tsx:52-66`。

**影响**：打开弹窗/Toast 的瞬间，恰好是动画起帧的瞬间，React 却在同步 render 整个侧栏 + 编辑器/画板；自动保存每次落盘后也会来一轮"全树 render + buildTree + syncTabs"。工作区越大、文档越长，单次提交越重。

### B3. 标签切换：先退场、再挂载重型编辑器、再入场

**机制**：`AnimatePresence mode="wait"` 会等旧视图退出（140ms）后才挂载新视图；新视图挂载时创建 Tiptap 编辑器（或 Excalidraw / React Flow），挂载工作与入场动画（140ms）在同一主线程上竞争。

**代码事实**：

- `AnimatePresence mode="wait"` + `key={activeTab?.id ?? "empty"}` + `motion.div` 全内容区 `opacity/y` —— `src/features/workspace/components/WorkspaceLayout.tsx:110-138`；
- `DocEditor` 用 `useEditor` 创建编辑器，扩展包含表格、代码块、Emoji、UniqueID 等 —— `src/features/editor/components/DocEditor.tsx:206-218`；
- Excalidraw 懒加载，首次打开仍需下载/初始化重型包 —— `src/features/board/components/BoardView.tsx:22-25`；
- 导图使用 React Flow 自定义节点，节点组件在选中/悬停时会重渲染 —— `MindmapTopicNode.tsx`。

**影响**：切换标签"感觉慢"通常不是动画时长问题，而是"退场 140ms + 挂载 + 入场 140ms"的串行结构，以及挂载期掉帧。

### B4. 指针热路径：O(块数) 布局读取 + 逐事件 React 状态

| 路径 | 代码事实 | 成本 |
|---|---|---|
| 块手柄跟随 | `measure()` 遍历全部顶层块，每块 `getBoundingClientRect()`，命中块再 `getComputedStyle`；监听器挂在编辑容器 `mousemove` 上 —— `useBlockHandle.ts:77-104`、`:178` | 鼠标在正文任意位置移动时，每次 mousemove 都 O(块数) 读布局；长文档尤其明显 |
| 块拖拽 | `computeDrop()` 在每个 rAF 里 `doc.forEach` 遍历全部顶层块并逐块 `getBoundingClientRect()` —— `useBlockPointerDrag.ts:117-140`、`:185` | 拖拽期间每帧 O(块数) 布局读取 |
| 文件树拖拽 | `dragover` 每次都 `setDropHint` 新对象，并调用 `resolveDropTarget` —— `useFileTreeDrag.ts:77-96` | 每次 dragover 重渲染整个 `FileTree`；大树上开销线性增长 |
| 图片缩放 | `pointermove` 每事件 `setDraftWidth` —— `AttachmentImageNodeView.tsx:120-127` | 每次指针事件触发 React render，未合帧 |

**影响**：这正是"拖动不丝滑/鼠标跟随发涩"的直接候选。它们与动画库无关，换 GSAP 不会减少 `getBoundingClientRect` 或 React 提交。

### B5. 布局结构：侧栏宽度瞬切 + 全页过渡

**代码事实**：

- `SidebarColumn` 折叠时外层宽度直接 `w-[var(--sidebar-w)]` ↔ `w-0`，只有内层做 `translateX` —— `src/features/workspace/components/SidebarColumn.tsx:14-19`。宽度变化会触发主编辑区整体 reflow（长文档重新换行），而侧栏内容同时滑出，视觉上容易"跳一下"。
- 标签切换的 `motion.div` 覆盖整块内容区，`opacity/y` 动画会给整棵编辑器子树建立合成层；在 120Hz 下这是很大的合成面积 —— `WorkspaceLayout.tsx:110-138`。
- `BlurFade` 在空状态动画 `filter: blur(6px→0)`（仅空状态，不属于主编辑路径，但说明"filter 逐帧动画"的写法存在）—— `src/components/common/motion/BlurFade.tsx:59-75`。
- 主题切换使用 View Transitions + `clip-path` 圆形揭示 500ms；WKWebView 是否支持取决于系统版本，不支持时直接切换 —— `src/lib/theme.tsx:73-95`。

### B6. 打字/保存期的周期性成本

- 每 500ms：`current.getJSON()` + `JSON.stringify` 写 localStorage（崩溃草稿）—— `DocEditor.tsx:660-665`、`documentDraft.ts:17-23`。长文档下序列化可能占用主线程数毫秒到数十毫秒。
- 每个按键：`setLiveCount(current.storage.characterCount.characters())` —— `DocEditor.tsx:656-658`。字数统计如果随文档长度线性计算，会在长文档上增加按键延迟（需确认 Tiptap characterCount 的实现）。
- 每次自动保存后：`applyDocumentSaved` → `setNodes` + `buildTree` + `syncTabs` → 全树 render（见 B2）；`InfoPanel` 还会因 `updatedAt` 变化重新请求知识网络。
- 这些成本不一定表现为"动画掉帧"，但会让用户感觉"整体不丝滑、不时卡一下"。

### B7. 启动/包体（次要，非交互动效）

- 构建产物主 JS chunk 约 2.1MB（minified），`dist` 约 10MB；Tiptap 编辑器不在懒加载范围内（Excalidraw 已懒加载）。
- 这影响首屏与首次打开标签，不是本次"拖动/弹窗"的主因；除非启动明显慢，否则不应优先动它。

### 7.3 决定

**不引入 GSAP。** 理由按权重：

1. **不解决瓶颈**：GSAP 是主线程补间引擎，不会消除 `backdrop-filter` 的合成成本、React 全树重渲染、重型编辑器重挂载、指针路径的布局读取。把它套在这些路径上，最多是"用另一种写法掉帧"。
2. **能力重叠**：本项目需要的是"进出场 + 弹簧 + 少量编排"，Motion 已经覆盖；GSAP 的强项（ScrollTrigger、SVG morph、复杂时间线）当前没有真实需求。001/002 报告也做过同样判断。
3. **许可证门禁**：`scripts/check-licenses.mjs` 的 PERMISSIVE 列表不含自定义 "no charge" 许可；引入 GSAP 会让 `npm run build` 的许可证检查进入 `unknown` 分支。即使人工豁免，也违反 AGENTS.md §5/§16 的依赖审批原则。
4. **第二套体系**：项目已经把动效预设收口在 `src/lib/motion.ts` 与 `tokens.css`；引入 GSAP 会破坏"单一动画来源"的约定，增加双套心智与包体。

**唯一值得重新评估的条件**（同时满足才考虑）：

- 出现明确的产品需求：复杂时间线编排、滚动驱动叙事、SVG morph，且 Motion 实测无法满足；
- 完成真机测量，证明确实是补间引擎能力不足（而不是合成/布局/React 成本）；
- 项目许可证策略允许自定义 "no charge" 许可，或取得 Business 授权；
- 接受包体增加与双体系维护成本。

### 7.4 如果只是想"更高级"的动效

不需要换引擎。更高性价比的顺序是：

1. 先把 CSS 动画统一到现有令牌；
2. 把浮窗/弹窗的"淡入"换成 Motion 弹簧（已有 `SPRING_PANEL`，只需扩大使用面）；
3. 控制同屏并发动画数量、位移幅度、模糊面积；
4. 只在高价值触点（空状态、统计数字、主题揭示）做"高级感"，正文编辑区保持静止。

这与 001/002 报告的设计守则一致，且不需要新增依赖。

### P1 · 消除每帧成本（需立项后改代码）

| 优先级 | 动作 | 预期作用 | 风险/备注 |
|---|---|---|---|
| P1-1 | 取消大面积实时模糊：弹窗遮罩/弹窗本体/信息浮窗改为不透明或静态渐变底；必须保留模糊时只留单层、限制半径与面积，禁止嵌套 | 直接降低弹窗/浮窗的合成成本；最可能把 30-50fps 拉回 60 | 视觉变更，需要 UI-SPEC 与设计确认；macOS 可评估原生 vibrancy，但不要用 CSS 模拟 |
| P1-2 | 建立渲染边界：`memo` 侧栏/文件树/行组件；把弹窗/Toast 状态与主布局隔离；文档保存只更新受影响节点；`syncTabs` 只在标题/类型变化时更新；避免每次保存 `buildTree` | 降低点击弹窗/自动保存时的整树提交 | 需要逐个确认 props 稳定性；不要机械 memo |
| P1-3 | 标签切换：保留每个标签的编辑器实例（keep-alive）或先挂载再动画；避免 `mode="wait"` 的"退场→挂载→入场"串行；全页过渡改为轻量页头/骨架过渡 | 降低切换延迟与挂载期掉帧 | 内存占用上升；需要限制保留数量/释放策略 |
| P1-4 | 指针热路径：块手柄按 rAF 合帧、缓存块 rect、只在进入手柄走廊或块变化时计算；块拖拽缓存 rect；文件树拖拽把落点提示移到单一浮层/DOM class，不逐 dragover 重渲染整树；图片缩放用 rAF + CSS 变量，pointerup 再提交 | 直接改善拖动手感 | 需要保证滚动/文档变更时缓存失效；手柄的定位精度要回归 |
| P1-5 | 侧栏折叠：不要在滑动的同时让主区宽度瞬切；可改为覆盖式滑出 + 主区固定宽度，或先完成宽度切换再滑内容（二选一，避免同帧重排+滑动） | 消除"跳一下"和重排掉帧 | 视觉/交互取舍，需要设计确认 |
| P1-6 | 减少动画面积：标签切换不要给整棵编辑器做 `opacity/y` 合成；只动页头/内容首屏或使用 View Transition 的快照（特性检测） | 120Hz 下合成面积显著下降 | 与 P1-3 一起做 |

### P2 · 打字期与次要成本

- 草稿保存：从 500ms 提到更长间隔/`requestIdleCallback`/IndexedDB，或只存增量；至少避免每次 `getJSON()+stringify` 全量写。

- 主题揭示：保留特性检测；WKWebView 不支持时直接切换。
- 包体：Tiptap 是否可按需加载、手动分包；这是启动优化，不是本次交互动效的主线。

### 9.2 页面内 rAF 采样

```js
(async () => {
  const deltas = [];
  let last = performance.now();
  let stop = false;
  const tick = (now) => {
    deltas.push(now - last);
    last = now;
    if (!stop) requestAnimationFrame(tick);
  };
  requestAnimationFrame(tick);
  await new Promise((resolve) => setTimeout(resolve, 5000));
  stop = true;
  const values = deltas.slice(1).sort((a, b) => a - b);
  const pick = (q) => values[Math.min(values.length - 1, Math.floor(values.length * q))]?.toFixed(2);
  console.log({
    frames: values.length,
    fps: (values.length / 5).toFixed(1),
    p50: pick(0.5),
    p95: pick(0.95),
    p99: pick(0.99),
    over16_7: values.filter((v) => v > 16.7).length,
    over8_34: values.filter((v) => v > 8.34).length,
  });
})();
```

说明：rAF 反映主线程帧回调节奏，能抓到 JS/布局阻塞；GPU 合成单独掉帧时，rAF 不一定完全等价，需同时看 Safari Timeline 的 FPS/Rendering 轨道。

## 10. 风险与未决问题

1. **模糊是设计语言的一部分**：`InfoFloat`、弹窗、导图面板的磨砂感来自 UI-SPEC；取消/降低模糊需要设计确认，不能单方面改样式。
2. **WKWebView 的 120Hz 能力未验证**：如果空闲 rAF 只有 60Hz，追 120 没有意义；先测平台上限。
3. **当前 e2e 调试实例不是性能基线**：debug + dev 的双重开销可能让结论严重偏悲观；必须先换档位。
4. **真实文档/文件树规模未知**：B4 的 O(n) 成本随规模放大；需要用户提供典型规模（例如 1 万字文档、1000 节点树）或在测试工作区构造。
5. **GSAP 许可**：即使项目方愿意人工豁免许可证门禁，GSAP 的 no-charge 许可仍限制"终端用户付费访问"，若 Starris 未来收费需重新评估；这不是纯技术问题。
6. **本轮未做真机帧采样**：所有"影响"均为机制推断；P1 落地后必须按 §9 复测，不能把"改完感觉快了"当作完成。
