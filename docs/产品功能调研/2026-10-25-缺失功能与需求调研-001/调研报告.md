## 1. 结论速览（TL;DR）

1. **当前最大的产品问题不是"功能少"，而是"入口承诺大于实际能力"**。顶栏搜索、快速跳转、打印、画板放映、表格/流程图、模板库、备份与恢复、语言切换、相关推荐等入口已经出现在界面上，但背后分别是 toast、空壳页、假数据或纯本地 state。其中"语言切换"和"相关推荐"会让用户误以为功能已经生效，比明确标注"即将推出"更伤信任。
2. **数据安全应排在功能扩张之前**。文档窗口关闭前没有 flush；打开旧工作区升级 schema 前没有数据库备份；文档保存没有版本冲突检测，且应用没有单实例保护；节点删除不可恢复。前三项在正常使用或升级路径上就可能丢内容，建议进入下一批。
3. **最值得投入的新能力是检索，不是表格/流程图/云同步**。星屿的核心价值是"把写过的东西再找回来"，而全局搜索、快速跳转、文档内查找目前都没有后端或索引。建议先做 FTS5 trigram 的中文 PoC，再决定索引范围。
4. **对象存储主体已闭环，剩余问题集中在垃圾回收完整性**：删除节点/知识库不会回收 `doc_block_hash`；`storage/objects` 下没有数据库行的文件不会被扫描；附件管理器列表没有分页；库附件按设计永久保留，只能靠 TTL 或手动删除。这些不会立刻损坏数据，但会随时间累积。
5. **不要把已拍板的产品决策当成 bug**：库附件不自动孤儿、无系统级全局热键、Excalidraw 原生键只读、附件节点不导入/不内联编辑/无版本历史、无节点级回收站、无云同步，都是已有文档明确写下的边界。若要翻案，应单独立项并重新设计，而不是顺手"补一下"。
6. **推荐批次**：批次 0"入口诚实化"（约半天到一天）→ 批次 A"数据安全"（约一周）→ 批次 B"检索与存储闭环"（两到三周）→ 批次 C"备份/恢复与导入闭环"（一到两周）→ 批次 D"体验扩展"→ 批次 E"战略能力"。搜索与表格/流程图不要同时开两条大线。

## 4. 关键缺口分析

### 4.1 入口诚实化：先停止"看起来能用"

这是成本最低、收益最直接的一批。当前至少有 6 处入口会让用户做出错误判断：

| 入口 | 实际行为 | 用户会怎么理解 | 建议动作 |
|---|---|---|---|
| 顶栏搜索胶囊 / `⌘⇧F` | mock toast；WKWebView 还可能吞掉组合键 | 以为能搜索 | 实现 R04a 前先禁用并标注"即将推出"，或直接上线搜索 |
| `⌘K` 快速跳转 | `available:false`，设置里标"即将推出"，但主界面仍可触发 mock | 以为能跳转 | 与搜索合并为命令面板，未实现前不占用快捷键 |
| 文档页头打印 | toast | 以为能打印 | 实现 R12 或暂时禁用 |
| `⌘P` 放映画板 | mock | 以为能放映 | 实现 R13 或暂时禁用 |
| 表格/流程图创建 | 能创建节点，打开是"即将推出"空壳 | 以为能编辑 | 在编辑器就绪前收起创建类型；已创建节点保留可删除 |
| 语言选择 | 改了本地 state，界面不变 | 以为切换成功 | 接 i18n；否则禁用并标注 |
| 信息面板"相关" | `MOCK_RELATED` 假文档 | 以为系统推荐了相关内容 | 立即撤下假数据；tab 可保留空态或隐藏 |
| 收藏空页 CTA | 点击走 mock | 以为能收藏当前文档 | 改为打开一个文档/提示先打开文档，或移除按钮 |

原则：**已出现的入口，要么真实可用，要么明确不可用；不允许假数据、静默无响应、或"看起来生效"的本地 state。** 这与上一轮文案精简的原则一致，也应作为后续 UI 验收项。

### 4.2 检索与导航：最值得做的新能力

**现状**

- 顶栏只有搜索外观，没有搜索命令（`lib.rs:43-90` 的命令清单中没有 search；全仓 Rust 无搜索实现）。
- 快速跳转只有 `available:false` 的动作与 mock 处理器（`actions.ts:12`、`useWorkspaceMainController.ts:419`）。
- 编辑器没有查找扩展；`editorExtensions.ts` 的扩展清单里没有 find/replace。
- 信息面板的"反向链接"只有空态，没有链接语法与索引；"相关"是假数据。

**用户场景**

1. 只记得一句话，不记得在哪篇文档/哪个知识库。
2. 记得文件名，想用键盘快速打开。
3. 长文档内想定位一个词并逐个跳转。

**技术方向（建议先 PoC，不直接定稿）**

- **索引源**：`node.title` + `doc_block_meta.markdown`（已有派生 Markdown 字段）+ 可选附件名。不要一开始索引画板元素 JSON。
- **索引方式**：SQLite FTS5 + `trigram` tokenizer，适合中文子串；若当前 bundled SQLite 不支持或索引膨胀过大，降级为 `LIKE '%kw%'` + 限制结果数。FTS5 属于 SQLite 内置能力，不新增 crate。
- **增量维护**：文档保存、节点改名、节点删除时同步索引；启动时校验索引版本，缺失则后台重建。不要用触发器把业务逻辑埋进 schema。
- **结果面板**：标题、类型、所在知识库、命中片段、更新时间；上下键/回车/Esc；点击打开并定位到块。
- **快速跳转**：复用同一面板，默认展示最近访问 + 标题前缀匹配，不单独做第二套 UI。
- **文档内查找**：ProseMirror 装饰高亮 + 上/下一处 + 计数；不要依赖 WKWebView 原生查找。

**验收要点**

- 中文 2 字查询可命中；标题/正文/文件名分别可搜。
- 删除/改名后无陈旧结果；重建索引不阻塞启动。
- 10,000 篇文档的基准下 p95 ≤ 150ms（先 PoC 实测；不达标就缩范围到标题+文件名，不要硬承诺）。
- 搜索面板键盘可完整操作，读屏能读出结果数与当前项。

**风险**

- 中文分词/索引体积是最大不确定项；trigram 对 1 字查询不友好，需要回退策略。
- 索引与正文一致性需要测试；最稳妥是保存事务后同步更新，失败则标记索引待重建。
- 不要为了搜索引入 Tantivy 这类重型引擎；当前数据规模用 SQLite 足够。

### 4.3 数据安全：正常使用路径上的缺口

**(1) 关闭窗口不 flush（R01，最高优先）**

- 文档自动保存是 1 秒防抖（`useDocumentPersistence.ts:17`），切换文档/标签/工作区前会 `flush`；但窗口关闭直接 `window.close()`（`src/lib/window.ts:11`、`WindowBar.tsx:43`），没有 Tauri `onCloseRequested`，也没有 `RunEvent::ExitRequested` 处理。
- 用户在输入后 1 秒内按红绿灯或 `⌘Q`，最后一次输入可能丢失；慢盘或锁冲突时窗口更大。
- 画板已有 `flush`，应复用同一关闭守卫；macOS 的 `⌘Q` 可能绕过窗口关闭事件，必须同时处理应用退出事件。

**(2) 迁移前没有备份（R03）**

- `migrate` 直接开启事务并执行 DDL；v10 还要重建 `node` 表、临时关闭外键（`db/workspace.rs:425-430`）。事务能保证正常失败回滚，但没有"迁移前的可恢复副本"，也没有用户可见的备份路径。
- 建议在 `user_version < SCHEMA_VERSION` 时：先 WAL checkpoint，复制 DB 到 `db/backups/`，保留最近 3 份；复制失败则中止迁移；迁移失败提示备份位置。备份策略要写入数据库设计文档。

**(3) 多实例与文档冲突（R22）**

- 画板保存有 `base_version` 检查（`board_service.rs:120-124`），文档保存只有 `node_id + document`（`models/document.rs:6-12`）。
- 应用未引入单实例插件（`src-tauri/Cargo.toml:22-23` 只有 opener/dialog），用户开两个实例指向同一工作区时，后保存者覆盖先保存者，且没有提示。
- 两个方向可以组合：应用级单实例（第二次启动聚焦已有窗口）+ 文档保存 `baseUpdatedAt`/内容版本冲突检测。单实例是更小的改动，但不能防外部进程/未来多窗口，建议两者都做。

**(4) 崩溃草稿（R23，可选）**

- 正常关闭由 R01 兜底；崩溃/断电仍可能丢最后一次防抖窗口。可在编辑时把草稿写入 `localStorage`，下次打开若草稿比 DB 新则提示恢复。成本低，但要注意多标签/多文档隔离与清理。

### 4.4 对象存储闭环：从"能删"到"删干净"

对象存储的主体设计已经成立：逻辑记录、内容寻址、引用表、软删、回收站、孤儿宽限、pack 压缩、看门狗都有。剩余问题不是主流程，而是边角回收：

1. **`doc_block_hash` 只在一篇文档保存时回收**。`document_service.rs:154-163` 会删除"该文档移除且全局无引用"的 hash；但删节点时只 `DELETE FROM node`（`node_repository.rs:230-234`），`doc_block_tree` 通过外键级联删除，`doc_block_hash` 没有级联，也没有维护任务扫描。结果是删除大量文档后，块内容仍留在 hash 表。建议在维护任务中增加 `DELETE FROM doc_block_hash WHERE NOT EXISTS (SELECT 1 FROM doc_block_tree ...)`，并补集成测试。
2. **`storage/objects` 下无 DB 行的文件不会被发现**。维护只清 `storage/tmp`（`attachment_maintenance_service.rs:199-238`）和 DB 中无引用 blob（`:101-108`）；`objects/big` 与 pack 文件若因崩溃/手工复制留下，没有扫描入口。建议增加"孤儿文件扫描"：只处理 mtime 超过 24 小时、且不在 `attachment_blob`/`attachment_pack` 中的文件；先移入 `storage/quarantine/` 保留 7 天，再删除，并在维护结果中报告数量/字节。不要在未确认时直接 unlink。
3. **维护删除物理文件与上传存在潜在竞态（未验证）**。维护在锁内删除 blob 行并提交，释放锁后才 `remove_big_object`（`:110-129`）；上传在锁内发现 blob 行不存在时，会把同哈希文件发布到同一路径（`attachment_service.rs:162-217`）。如果 unlink 发生在上传发布之后，就会删掉刚写好的文件，留下有 DB 行但磁盘缺失的附件。建议先用并发测试复现；修复方向是把 unlink 放进锁内，或先原子改名到 tombstone 再在锁外删除，且删除前重新确认该 hash 仍无 blob 行。
4. **库附件按设计永久保留**。`node_attachment_repository.rs:86-101` 只对 `scope=node` 标孤儿；`library` 附件即使无引用也不会自动进入回收站。这是明确决策，不应改；但应在 UI 上持续展示"未关联数量/可回收字节"，并提供批量删除/设置 TTL 的入口（当前 TTL 只在 上传时设置，见 `AttachmentManager.tsx:89-103`；`set_lifecycle` API 已存在但 UI 未接编辑）。
5. **保留期硬编码**。7 天/30 天/24 小时/6 小时是常量（`attachment_maintenance_service.rs:26-33`）。是否要做成设置项，取决于产品是否需要不同工作区的不同策略；不要为了"可配置"而增加一堆用户不理解的开关，至少先保持默认并写清语义。
6. **看门狗只在应用运行期执行**。启动跑一轮、之后每 6 小时（`:158-180`）；应用关闭期间 TTL 不会兑现。这是本地应用的合理边界，但文案应说"到期后将在下次维护时清理"，而不是"到期立即删除"。
7. **附件列表无分页**。`attachment_repository.rs:179-198` 一次返回全部匹配行；附件多时 UI 会卡。建议加 `limit/offset` 与名称/目录搜索，统计仍走单独聚合查询。

### 4.5 内容结构：模板、历史、回收站、导入

- **模板库（R09）**：目前只有菜单占位。最小闭环不需要市场/变量系统：内置若干文档/画板模板 + 把当前文档/画板"另存为模板" + 创建时选择。模板可先存工作区文件，不必新增复杂表。
- **文档历史（R10）**：当前没有版本字段/历史表；块级内容寻址已有去重基础，适合做"快照只存块引用"的历史。建议先做手动快照 + 定时快照 + 恢复为新版本，不要一开始做逐字符 diff。
- **节点回收站（R11）**：与已拍板的"不做节点级回收站"冲突。若用户对误删文件夹有强需求，再立项；实现上可复用附件的软删/宽限思路，但会涉及 schema v11、树路径、收藏、搜索索引、附件引用的联动，成本不低。
- **附件节点导入（R08）**：导出已经写入 `attachmentNodes`（`export_service.rs:322-360`），导入却不接受附件文件（`import_service.rs:605-620`），"导出→导入"不闭环。附件树需求文档把它列为"不做"，所以这是**决策复核项**：要么明确写"导入不恢复附件节点"，要么补导入并写清冲突策略。
- **表格/流程图（R16）**：当前能创建但视图是占位。短期最合理的动作不是马上写两个编辑器，而是**先收起创建入口**，避免制造无法使用的节点；中长期可评估"表格节点复用文档编辑器 + 流程图复用画板预设"这两条低成本路径，再决定是否自研专用编辑器。
- **打印/放映（R12/R13）**：都属于"小能力、明确承诺"的类型。打印可先走系统打印/打印 CSS 或复用 PDF 导出后打开；放映可先做全屏 + 适配内容 + Esc 退出，不要一开始做多页演示文稿。
- **反向链接/相关（R15）**：需要先有内部链接语法与索引；在搜索索引落地前做，会重复建一套内容解析。建议排在 R04 之后。当前最紧急的是撤掉 `MOCK_RELATED`，不要让假数据继续出现。
- **界面语言（R14）**：如果近期没有国际化目标，最合理的动作是禁用/移除选择器；如果要做，需要 UI 文案全量抽取、日期/数字格式、布局回归，成本远大于一个下拉框。

### 4.6 安全与性能：发布前要处理，不是现在的第一优先

- **CSP 为 null**（`tauri.conf.json:29-31`）。本地单用户应用的风险模型较低，但一旦分发或引入外部内容（导入 HTML、社区组件库、远程图片），CSP 是基础防线。收紧时要回归 Excalidraw 的内联样式、Blob 图片、Tiptap 内联样式。
- **`export_write_file` 接受任意绝对路径并可覆盖**（`export_service.rs:528-551`）；上传/下载/导入也接受前端传入的绝对路径。当前这些路径都由系统对话框产生，但命令层没有"路径来自用户选择"的约束。若前端被 XSS/恶意导入内容攻破，理论上可写用户有权限的任意文件。建议在威胁模型明确后，加路径白名单/一次性令牌或限制到用户选择目录。
- **日志记录完整导出路径**（`export_service.rs:574-580`），属于隐私/目录结构泄露，低危，但容易修。
- **性能**：附件列表无分页、维护逐行查询是最明确的两处；统计是一条包含多个标量子查询的 SQL（`attachment_repository.rs:484-506`），当前规模可接受，数据量大时再评估。不要在没有基准的情况下引入缓存层。

## 7. 风险与未决问题

### 7.1 需要运行时复现/验证

1. **维护删除与上传竞态（R02）**：当前只是调用链推断。必须先写并发复现（同哈希大文件 + 在 unlink 前注入延迟），确认是否真的能产生"DB 有行、磁盘无文件"；未复现前不要大改锁范围。
2. **搜索中文效果与索引体积**：FTS5 trigram 对 1 字查询、标点、英文混排的表现需要 PoC；索引体积可能接近正文大小，要量。不达标时降级到标题/文件名搜索，不要硬撑。
3. **多实例行为**：单实例插件接入后，第二次启动是聚焦还是新开窗口；macOS `⌘Q`、Dock 退出、系统重启的路径都要测。
4. **CSP 收紧后的兼容性**：Excalidraw 内联样式、Blob 图片、Tiptap 内联样式、PDF 导出可能触发 CSP；需要 9 主题 × 深浅回归。
5. **备份格式的向前/向后兼容**：新版本必须能读旧备份；旧版本读到新备份应明确拒绝，而不是半恢复。
6. **存储孤儿扫描的误删风险**：活跃上传的临时文件名、pack 正在 compaction、quarantine 清理都要有测试；不能只按"不在 DB"判断。

### 7.2 需要产品拍板

1. **下一阶段主线**：数据安全 vs 检索 vs 内容结构化。我的建议是"数据安全 + 检索"，表格/流程图/云同步延后。
2. **节点删除是否要可恢复**：当前是硬删除 + 确认；如果目标用户经常整理文件夹，回收站可能比文档历史更值得做。
3. **语言选择**：近期是否有英文/日文用户？没有就移除/禁用，不要留假控件。
4. **附件节点导入**：导出已支持附件节点，导入明确"不做"；是否要闭环？如果要，冲突策略（同名/同路径/同对象）需要定义。
5. **工作区备份形态**：单文件压缩包还是目录复制？是否需要加密？是否要跨版本恢复？
6. **发布范围**：只给自己/可信用户，还是要分发？这决定 R18 的优先级与威胁模型。
7. **表格/流程图的产品定位**：是"文档里的表格块"、"独立表格节点"，还是"画板里的流程图模板"？不同定位成本差一个数量级。
8. **保留期是否需要可配置**：如果只有一种合理默认值，不要增加设置项；如果有企业/团队场景，再考虑。

### 7.3 本报告不涉及

- 外部竞品的功能/价格/市场份额结论；
- 真实用户访谈与可用性测试；
- 云同步/协作的服务端架构与合规；
- 表格/流程图编辑器的完整选型；
- 任何代码实现与排期承诺。
