## 1. 背景与目标

Starris 目前是纯"手工"的本地优先知识库：所有能力都是"用户主动做一次"（新建、编辑、导出、备份、清理）。R01–R23 的调研已把这类单次动作补齐，剩下没被覆盖的一类需求是**重复性、规则性、定时性的劳动**。

本次调研要回答三个问题：

1. 当前架构离"能跑一条流程"还差哪些地基，哪些地基已经白送。
2. 成熟自动化软件（n8n / Node-RED / Keyboard Maestro / Hazel / Notion Automations / Power Automate / Raycast）值得抄的到底是哪一层——是节点数量，还是它的可观察性与安全模型。
3. 在这个桌面笔记 app 上，自动化有哪些值得开发的方向，以及各方向的权限代价。

### 2.3 一条架构纪律（会直接决定执行器性能设计）

AGENTS.md §1.1 把"批量数据处理、性能敏感计算"划归 Rust；§6.2 要求"大数据处理优先在 Rust 端分批、流式或增量，避免整份数据在前后端反复复制"。

推论：**xyflow 只是编辑器和状态可视化层，绝不能当执行引擎。** 画布上那份 DAG JSON 是"程序"，跑它的是 Rust。若在前端逐节点 `invoke`，等于每步两次序列化 + 两次 IPC 往返，10 万行结果集会直接卡死交互线程。

## 3. 成熟自动化软件拆解

### 3.1 它们的共性骨架（值得照搬的概念模型）

七家产品看下来，抽象出来是同一套六元组，差别只在节点多寡与宿主环境：

```
Trigger(触发器) → Context(变量与数据流) → Action(动作) → Predicate(条件/分支) → Sink(落地/投递) → Run Ledger(执行历史 + 重试)
```

其中被反复低估的两块，恰恰是"自动化可信不可信"的分水岭：

- **Run Ledger（执行历史）**：n8n 每一次执行都可展开成"逐节点输入/输出快照 + 耗时 + 错误"，还能"用同样的输入重跑"。国内桌面工具（Keyboard Maestro）也有 action 日志。
- **单步调试**：n8n / Node-RED 允许"只跑到这个节点"，把中间结果摊开。这是用户敢把流程交给后台的根因。

### 3.2 对比矩阵（含能否直接复用的判定）

| 产品 | 定位 | 真正值得借鉴的一点 | 能否直接复用 | 判定依据 |
|---|---|---|---|---|
| **n8n** | 服务端 workflow 引擎，20.8 万 star | 单步执行 + 执行历史 + Error Workflow（失败走另一条流程）；"Schedule Trigger 参数化 cron + 时区"的交互 | ❌ **License 不合规** | GitHub API 实测 `license = NOASSERTION`（其实际为 Sustainable Use License，fair-code 而非 OSI 开源，限制商用托管/再分发）。闭源分发的桌面 app 内嵌其代码/节点有法律风险 → **只借交互模式，不引代码** |
| **Node-RED** | Node.js 流式编排 | 消息（msg 对象）在节点间流动 + 注入/调试节点，"上下文对象"模型很干净 | ❌ 运行时不匹配 | Apache-2.0 许可其实可用，但它是 Node.js 服务端运行时，Tauri 内没有 Node，且 §1.1 要求重逻辑在 Rust |
| **Windmill / Automatisch** | 服务端自动化 | 把流程参数当作"类型化 app 参数"，表单自动生成 | ❌ AGPL 传染 | 需真实开发机复核（本机 GitHub API 不可达，见 §9） |
| **Keyboard Maestro** | macOS 宏引擎 | **Trigger 的种类远比想象多**：热键、输入字符串、指定 app 激活、登录、系统唤醒、剪贴板变化、定时……约 15 类触发器 + 近百动作 + 宏分组开关 + AppleScript/Python 脚本混编 | ✅ 概念可抄 | 商业闭源，只作交互参照。它的"宏分组可整体启停"值得直接抄进流程管理 |
| **Hazel** | 文件夹规则 | **零画布**："文件落入某目录 → 按条件自动处置"。把自动化的心智成本降到最低 | ✅ 设计思路可抄 | 结论：最简单的自动化不该强制用户画图，**规则表比画布更适合 L1 场景**（见 §6 约束创新） |
| **Notion Automations** | 属性变化触发 | "状态变化即触发"，用户完全不感知编排；数据库视图即自动化入口 | ✅ 概念可抄 | 对 Starris 的映射：节点加标签 / 移动 / 状态变化 → 触发流程 |
| **Obsidian Dataview / Bases** | 查询即视图 | **在文档里写查询，打开时重算**——不生成静态副本，永远新鲜 | ✅ 最契合本地优先 | 这是比"定时报告"更轻的产品形态（见 F13），且和本地 SQLite 天然匹配 |
| **Power Automate Desktop** | 企业 RPA | UI 元素拾取（把"点哪个按钮"抽象成可重放的语义选择器，而不是像素坐标） | ⚠️ 代价极高 | Starris 走这条路等于做通用 RPA，与笔记主业背离；且像素级键鼠模拟在 macOS 上要辅助功能权限 + 分辨率脆弱 |

### 3.3 差异化判断（不跟牌的地方）

1. **竞品都是"连接器数量"竞赛，Starris 不应该跟。** 拼 n8n 的 400+ 集成必输。本地优先的差异化在**"流程能读写你自己的知识库、你的本地文件、你的本地数据库"**，而且数据不出机器。
2. **竞品默认"云端跑"，Starris 只能"本地跑"——这是约束也是卖点。** 卖点是"定时任务在你电脑上，断网也能跑"；约束是必须诚实处理"电脑休眠/关机时错过的触发"（见 §7 反向脑暴）。
3. **竞品没有"文档 + 富文本 + 导出"链路。** Starris 已有的 MD/HTML/DOCX/PDF 生成 + 模板 + 附件对象存储，是通用自动化平台反而缺的下游能力。**把"生成一份有排版的文档"当作自动化的终点，是本项目独占的组合优势。**

## 4. HMW 问题重述

> **我们如何能让本地优先的知识库用户，在零代码、且数据不出机器的前提下，把"每周重复的取数—汇总—成文—投递"变成一次配置、长期复用、可审计的流程？**

拆解出的子 HMW：

- HMW 让用户**相信**后台自动跑的东西没弄坏他的数据？→ 执行历史 + dry-run + 回收站/快照兜底（R10/R11 已备好）。
- HMW 让"配置一条流程"的心智成本低于"手写一个 shell 脚本"？→ 复用模板库做预设流程（Hazel 式规则 + n8n 式画布分层）。
- HMW 在不放开 shell 权限的前提下拿到 80% 的自动化收益？→ L1–L3 层全部零新权限（这是本报告的核心发现）。

## 6. 5 Why 根因追问

### 链路 A：用户为什么要"定时报告"

> 痛点：每周手写周报，要从各知识库翻笔记。

- Why1 因为笔记分散、要人工找 → Why2 因为"哪些笔记属于本周"这个规则只在脑子里，产品里没地方表达 → Why3 因为产品只有"写"的原语，缺"查询 + 聚合"的原语 → Why4 因为 `search_index` 已经建好了，但只服务全文检索，没暴露成可组合的查询动作 → **Why5 根因：数据完全结构化在 SQLite 里（type/path/word_count/时间戳都在），但产品层没有"把它当一个数据集"的入口。**

  → 解法（比"做个报告功能"更根本）：**F19 SQL/查询节点**是一等公民，报告只是它的一个消费者。

### 链路 B：用户为什么不敢开自动化权限

> 痛点：现在的 capabilities 只有 8 项、极窄，这是有意为之（R18 安全加固）。一旦为了自动化放开 shell/键鼠，这个 app 的安全属性就变了。

- Why1 因为怕失控 → Why2 因为授权是"一次性、全局、无审计"的 → Why3 因为没有"这一条流程到底会碰什么"的可见声明 → **Why5 根因：缺一个声明式的"能力清单 + 执行台账"，而不是缺权限。**

  → 解法：**F06 每条流程保存自己用到的能力清单**（读哪些路径 / 执行哪些动作），首次运行显式确认；每次执行写 `flow_run` 台账并落 `logs/`。这一条把"放开权限"从"信任崩塌"变成"可审计的交换"。

### 链路 C：为什么"自动化"容易做成玩具

- Why1 因为做了画布但没地方可去 → Why2 因为动作太少 → Why3 因为把"能连外部世界"当成前提 → **Why5：真正的根因是"下游落地链路不够长"。而 Starris 恰好已有完整的文档生成 + 导出 + 落盘授权链路，这是别的画布类产品要补的，这里已经现成。**

  → 结论：**先做"闭环到自己文件里"的自动化**（生成文档/表格/报告/巡检结果），再考虑跨应用。

## 7. 反向脑暴：怎样让这个功能一上线就被骂，以及逆转

| 恶化方案 | 逆转出的设计要求 |
|---|---|
| 后台偷偷跑，改了用户数据也没人知道 | 每次执行必写台账 + 系统通知（L5 后可选）；破坏性动作默认先 dry-run 出清单再执行 |
| 节点参数是一坨 JSON 文本框，改字段要手写转义 | 每个节点必须有类型化表单 + 默认值 + 合法范围 + 即时报错（AGENTS.md §8 对配置的要求） |
| 出错就整条停，还不知道停在哪 | 节点级红绿高亮 + 单节点重试 + 可选"失败即中止 / 跳过继续"策略 |
| 电脑关机期间错过的定时任务，下次开机一口气补跑 30 次 | 落库 `last_fired_at`，错过的合并成一次；策略显式可选（错过即跳过 / 只补最近一次） |
| 允许流程塞任意 shell 命令，等于把整台电脑交给一个 JSON 文件 | 动作走白名单 + 参数类型化；任意命令必须是显式的"开发者节点"，默认关闭、每次运行确认、日志留痕 |
| 键鼠模拟抢走焦点，用户正在打字被截断 | 桌面级注入只在用户手动点"运行"后生效；优先 AppleScript / 无障碍 API 这类语义级动作，不用像素坐标 |
| 每一步走 IPC 传大 JSON，10 万行时 UI 卡死 | 管道在 Rust 内传递，行集存临时表或文件，前端只拿游标 + 摘要；执行走 `#[tauri::command(async)]` + `spawn_blocking` |
| 流程改坏了没法回退 | 流程本体是 `node`，直接继承 `doc_history` 快照与回收站（R10/R11），零额外成本 |
| 定时逻辑在前端 `setInterval`，切到别的窗口就不跑 | 调度归 Rust，前端只读 `next_fire_at` 做展示 |

## 8. 约束创新（这一节产出了本报告最重要的发现）

| 设定约束 | 在约束内能做的 |
|---|---|
| **"不新增任何 Rust 依赖、不动 capabilities"** | 定时聚合自有 SQLite → 生成 MD/HTML/DOCX/PDF → 写进已授权的同步文件夹 → 存成笔记；批量重命名/移动/打标签/字数统计；知识库健康巡检；备份轮换与保留清理；导入流水线。**→ 这一整批足够构成 v1，且完全不触碰安全边界** |
| **"只有一周开发时间"** | 只做 1 个触发器（定时器）+ 1 个动作（导出一篇文档到指定目录）= "每天 09:00 把《日报》导出成 PDF 到桌面"。用最小切片验证执行器 + 调度 + 权限三件事 |
| **"只能改一行代码级别的杠杆"** | 把 `flow` 节点的存储从 `board_scene` 切到 `flow_definition`——这一个动作决定了后面所有功能"要不要新造一套文件类型/迁移/回收站/搜索集成"。答案是都不需要 |
| **"如果让用户来设计"** | 用户先要的大概率不是 RPA，而是"我这一周写的笔记，明天早上自动变成一篇日报" |
| **反转约束："流程不是一个文件，而是文档里的一个块"** | 嵌入式动态查询块（Obsidian Dataview 式）：好处是不用切窗口、永远新鲜、写起来像公式；代价是 xyflow 画布塞在小容器里体验差 → **两者不冲突，分成 F13（块，零画布）和 F01–F07（画布，有编排）** |

## 12. Top 3 推荐

### 推荐 1：F01–F08「编排内核 + 定时报告流水线」（把用户原话里的四件事一次做完）

- **描述**：`flow`（type=5）节点从"画着看"升级为"能跑"。内核是 4 类节点起步 —— **触发器（定时/cron）→ 数据源（自有 SQLite 查询 / 笔记集合）→ 变换（聚合、模板填充）→ 落地（生成 MD/HTML/DOCX/PDF，写进已授权目录，并存成一篇笔记）**。Rust 侧跑 DAG，xyflow 侧只负责编辑、参数表单、执行时的红绿高亮。
- **解决的痛点**：用户明确提出的"定时报告 / 文档表格生成 / 定时连接数据库统计"三条，全在这一条链路里；而且**一条都不需要动 capabilities**（§2.2 的关键发现）。
- **为什么先做它而不是先做桌面自动化**：它的下游（导出、模板、落盘授权、快照、回收站）100% 已存在；它的上游只需 F02/F04/F05 三件基建。做完它，"加一个新自动化"从"加一个页面"降级成"加一个节点"。
- **实现路径（不含代码，仅供后续需求文档参考）**：新表 `flow_definition` / `flow_run` / `flow_node_run` → `services/flow_service.rs` 执行器 + `std::thread` 调度（同构于 `attachment_maintenance_service.rs`）→ 新 `#[tauri::command(async)]` 命令族 + `flow://run-progress` 事件 → 前端 `src/features/flow/`（xyflow 画布 + 节点属性面板 + 执行历史抽屉）。
- **验证方式**：单测覆盖 DAG 拓扑/环检测/上下文插值；真机 E2E 覆盖"配一条每周日的报告流程 → 手动跑一次 → 看历史 → 改错一个节点看红绿 → 等定时自动触发一次"；台账与 `logs/` 留痕。
- **风险**：① F05 事件流是硬前置，没有它长任务无反馈（现状只有 2 个 emit）；② 执行器易长成"什么都往 Rust 塞大 JSON"，需一开始就定"行集存临时表 + 只传游标"的约定；③ 调度器同步命令会占主线程 —— 按既有结论，先加 `#[tauri::command(async)]`，别把"挪出主线程"误当成"获得并发"（状态仍持锁、仍单连接）。

### 推荐 2：F10 + F09「知识库自动巡检 / 批量整理」—— 内核最好的自我验证用例

- **描述**：定时扫描库内问题（孤儿附件、无标题、重复标题、正文引用的图失效、超长文档、未归档），产出一篇"巡检报告"笔记；同一套动作节点反过来做批量整理（改名/移动/打标签）。
- **解决的痛点**：库越大越没法靠手感治理；而且治理是"读多写少"，风险最低。
- **预期效果**：把附件治理（R05/R06/R21 已有底层）从"用户主动点清理"变成"每周自动告诉我有啥问题"。
- **为什么排第二**：它几乎不需要新节点类型，是内核对**已有 78 个命令**的一次直接编排——最快能看出 F02 执行器设计得对不对。
- **风险**：写型动作必须默认 dry-run，先出清单再执行（§7 逆转要求）。

### 推荐 3：F13「文档内动态查询块」—— 竞争壁垒形态，比画布更轻

- **描述**：在 Tiptap 文档里插一个"查询块"，写下条件（本周 / 某知识库 / 含某标签 / 字数阈值），打开时实时重算成表格。不生成静态副本，永远新鲜。
- **解决的痛点**：5Why 链路 A 的根因（数据在 SQLite 里但产品没有"当数据集用"的入口），而且比"定时生成报告"少一层编排。
- **预期效果**：用户不学任何编排，就能得到"动态目录页 / 本周写了啥 / 待办清单"。
- **风险**：需要新鲜度策略（缓存 + 重算时机），不能每次打开全表扫描（§6.4 索引要实测）；**这条与推荐 1 不冲突，是同一个查询节点（F20）的第二个消费者**。

## 13. 被放弃的创意（存档参考）

- **F37 键鼠模拟 / 通用 RPA**：`enigo` 3.75M 总下载低于选型门槛；要 macOS 辅助功能权限；像素坐标随分辨率/主题失效；与"本地知识库"主业背离。放弃原因——代价高、收益与产品定位无关。
- **F38 UI 元素拾取**：等于自研 Power Automate Desktop，工程量数倍于整个 Starris。
- **内嵌 n8n / Node-RED / Windmill 作为执行引擎**：n8n 实测 `NOASSERTION`（fair-code）不可内嵌；Node-RED 需 Node 运行时、违反 §1.1；Windmill/Automatisch 若为 AGPL 则有传染风险（待复核）。放弃原因——**外部引擎这条路在 Tauri 桌面闭源分发场景下没有干净解**。
- **F35 自由 shell 命令节点**：AGENTS.md §9 直接禁止"执行来自用户输入的任意命令"。放弃原因——不做自由命令，将来只做受限白名单动作。
- **流程用独立文件类型（不进 `node`）**：放弃原因——会白丢搜索、收藏、标签、历史快照、回收站、备份、导出六项已有能力。
- **"拼连接器数量"**：放弃原因——和 n8n 正面比数量必输；差异化在"数据不出机器 + 读写你自己的知识库"。

## 14. 风险与未决问题

| 类别 | 条目 | 是否阻塞下一步 |
|---|---|---|
| 安全边界 | 进入 L5 意味着 `capabilities` 从 8 项扩张，改变这个 app 一贯的窄授权姿态（R18 是刻意收紧的）。**需用户明确决策**：这个 app 要不要成为"能操作整台电脑"的软件 | **是**（影响是否需要 F06 能力清单设计的严格程度） |

| 平台约束 | "本地跑"必然面对：合盖休眠、关机、时区变更、错过的触发。misfire 策略是产品决策不是技术细节 | 否（有保守默认方案：合并成一次） |
| 技术前置 | 无进度事件流（现状 2 个 emit）。L0 的 F05 必须和 F02 同期落地，否则长任务体验不达标 | **是**（属实现前置，非需求歧义） |
| 许可待复核 | Rust crate 的 license 与 star **未在本机验证**（GitHub API 不可达 http=000、crates.io 许可字段被镜像剥离）。见 §9 | **是**，需在真实开发机 `cargo deny` / `cargo license` 复核后才能立项引依赖 |
| 产品口径 | v1 是否要"零新权限"这条硬约束作为卖点（数据不出机器 + 不动安全边界）？ | 是（决定 v1 边界） |
| 需求冲突 | `flow`（type=5）现在承载"画板流程图"用途且有 E2E 22 / Rust 集成测试覆盖。改成 DAG 是**破坏性行为变更**——需要决策：迁移旧数据 / 新增 type=8 / 用开关共存 | **是**（数据结构 + 不可逆操作，按 §23 必须先问） |
