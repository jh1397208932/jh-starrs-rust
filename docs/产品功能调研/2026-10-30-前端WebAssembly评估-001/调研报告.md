## 1. 结论速览（TL;DR）

1. **当前不建议引入 WebAssembly。** 不是"WASM 不够快"，而是本项目前端侧真正无法下移的热点，绝大多数根本不是"算力不够"，WASM 帮不上或代价更大。
2. 无法下移 Rust 的前端热点只有三类：
   - **浏览器排版/几何/绘制绑定**：字体测量、`getBoundingClientRect`、SVG/Canvas 光栅化、合成与绘制。WASM 拿不到这些浏览器结果，完全无能为力。
   - **前端对象图上的每次交互遍历**：ProseMirror 文档、树结构、布局数据。数据在 JS 堆里，进 WASM 必须先做对象图编解码，通常比计算本身更贵。
   - **React 提交与重型视图挂载**：不是计算问题，WASM 不参与。
3. WASM 只在**同时满足**三件事时才会赢：纯数值/字节计算、数据常驻 WASM 线性内存（TypedArray）、且必须跑在 WebView 里无法交给原生。本项目目前**没有这样的内核**。
4. 反过来，凡是能表达成"数据进、结果出"的计算，**原生 Rust 几乎总比 WASM 快**：没有模块下载/实例化、没有 WKWebView 线程限制、可以多线程、可直接读写文件与数据库；而且项目已经有 raw bytes IPC 通道（`src/api/client.ts:48-68`、`src/api/attachment.ts:133-139`），大数据不必走 JSON。
5. 逐场景结论（详见 §4）：
   - 导图文本测量/布局、编辑器每键 DOM 依赖、字数与崩溃草稿、预览光栅化、文件树装配、指针热路径、渲染合成——**全部不适合 WASM**，应做 JS 级修复（Canvas 测宽、事务增量、空闲调度、缓存 + rAF）。
   - 搜索、导入导出、附件与图像处理、备份、AI——**已经在 Rust**，用 WASM 反而回退。
6. **一条额外的硬约束（本次新发现）**：生产 CSP 是 `script-src 'self'`，不含 `'unsafe-eval'`/`'wasm-unsafe-eval'`，而 `devCsp` 为 `null`（`src-tauri/tauri.conf.json:36-39`）。按 CSP3 规范，这会在打包后**拦截 WASM 编译**，而 Vite dev 下却正常——WASM 会出现"开发可用、真机被拦"的假阳性。引入 WASM 必须先放松 CSP，并在 WKWebView 真机验证关键字支持（**未验证**）。
7. 值得保留的未来候选只有：应用内 PDF 页面渲染、本地模型推理、像素级图像处理。且应**先评估原生 Rust / 系统能力**，WASM 仅当计算必须留在 WebView 时才考虑。准入清单见 §6.3。

## 2. 判据：WASM 何时才值得

### 2.1 五条硬条件（同时满足才立项）

| 编号 | 条件 | 说明 |
|---|---|---|
| C1 | 计算是纯数值/字节，**数据能常驻 WASM 线性内存** | 最好全程 TypedArray；不能每次调用都把对象树序列化进/出 |
| C2 | 单次计算足够重，或调用频率足够高 | 经验门槛：单次 > 数 ms，或每帧都要跑且 JS 在帧预算内做不到；本项目 120Hz 预算 8.3ms/帧、60Hz 16.7ms/帧 |
| C3 | 计算**必须**在 WebView 里发生 | 依赖 DOM/字体/Canvas/交互帧，原生 Rust 拿不到或往返成本更高 |
| C4 | 收益可测量且大于成本 | 同构建、同场景、多次采样；包体、构建链、CSP、维护成本一并计入 |
| C5 | 算法只有一份权威实现 | 共享 crate 或明确单一实现，不能 native 与 wasm 各写一套（AGENTS.md §7） |

### 2.2 三种执行环境对比（针对本项目）

| 维度 | 前端 JS | 前端 Worker / OffscreenCanvas | 前端 WASM | 原生 Rust（Tauri IPC） |
|---|---|---|---|---|
| 对象图数据 | 零拷贝 | 结构化克隆（深拷贝） | 需手工编解码 | 需 serde/JSON 或 raw bytes |
| 大块二进制 | 一般 | 可 transfer | 可共享线性内存 | `tauri::ipc::Response` raw bytes |
| 线程 | 主线程 / Worker | Worker 1 条 | 依赖 SharedArrayBuffer + 跨源隔离（**未验证**） | 可任意线程/线程池 |
| 文件/数据库/系统 | 无 | 无 | 无 | 完整 |
| 启动/包体成本 | 0 | 小 | 模块体积 + 实例化 | 已在包内 |
| 可调试性 | 最好 | 中 | 差（WASM 帧/内存） | 好（Rust 日志/调试器） |
| 适合负载 | DOM、交互、对象图 | 序列化、离屏绘制 | **常驻数值内核** | 所有"数据进、结果出"的重计算 |

**判据一句话**：能下移 Rust 的，不用 WASM；必须留 WebView 但依赖 DOM/字体/绘制的，WASM 也做不了；只有"必须留 WebView + 纯数值 + 数据常驻"三者同时成立，WASM 才是正解。本项目当前没有任何一个热点满足。

## 3. 现状事实

### 3.1 职责边界已经正确（代码事实）

- 项目规范明确：复杂算法、批量数据、性能敏感计算放 Rust（AGENTS.md §1.1）。
- Rust 已承担：搜索（SQLite FTS5 + 短词 LIKE 回退，`src-tauri/src/services/search_service.rs:1-40`、`src-tauri/src/db/workspace.rs:231`）、导入（md/docx/office/PDF 文本，`Cargo.toml:35-39,48`）、导出（md/html/docx/pdf，`Cargo.toml:37-38`）、字数计算与持久化（`src-tauri/src/repositories/document_repository.rs:55-66`）、附件存储与哈希（blake3）、图片处理（`image` crate，`Cargo.toml:39`）、导图格式、AI、备份。
- 前端已有 raw bytes IPC：`invokeRawCommand`（`src/api/client.ts:48-68`）与附件上传（`src/api/attachment.ts:133-139`）；Tauri v2 官方支持用 `tauri::ipc::Response` 返回 ArrayBuffer 绕过 JSON 序列化（来源见附录 B）。

> 这三条合起来意味着：**"把计算搬到原生 Rust" 这条路在本项目里是低摩擦、已被验证的**；WASM 只会成为第三种执行环境，而不是唯一的性能出路。

### 3.2 无法/不宜下移 Rust 的前端热点清单

| 编号 | 热点 | 性质 | 能否下移 Rust | WASM 判定 |
|---|---|---|---|---|
| H1 | 导图文本测量 + 布局 | 浏览器字体/排版绑定 | 测量不能；布局能但不值得 | 不适合 |
| H2 | 编辑器每次 docChanged 的 TOC/大纲 | DOM + ProseMirror 对象图 | 不宜（每键序列化更贵） | 不适合 |
| H3 | 字数统计 + 崩溃草稿 | 对象图 + JSON 序列化 | 草稿可以，但非 WASM 问题 | 不适合 |
| H4 | 预览/SVG 光栅化 | 浏览器 SVG/Canvas/字体绑定 | 可部分下移（resvg），有字体一致性代价 | 不适合 |
| H5 | 文件树装配/排序/复用 | 纯 JS 对象数组 | 可以，但规模不值 | 不适合 |
| H6 | 指针热路径（块手柄/拖拽） | DOM 几何 | 不能 | 不适合 |
| H7 | 渲染/合成/重型视图挂载 | 浏览器渲染管线 | 不能 | 无关 |
| H8 | 语法高亮 | 纯字符串处理 | 可以（syntect），但输入小 | 暂不 |
| H9 | 搜索/导入导出/附件/AI | 数据与文件处理 | **已下移** | 反而回退 |
| H10 | PDF 页渲染 / 本地推理 / 像素处理 | 未来候选 | 优先原生 | 条件性 |

### 3.3 关键新发现：生产 CSP 会拦截 WASM

- `src-tauri/tauri.conf.json:36-39`：
  - `devCsp: null`（开发态不注入 CSP）；
  - 生产 `csp` 的 `script-src` 只有 `'self'`，没有 `'unsafe-eval'`，也没有 `'wasm-unsafe-eval'`。
- CSP3 规定：只要页面存在 CSP 且 `script-src`（或 `default-src`）既不含 `'unsafe-eval'` 也不含 `'wasm-unsafe-eval'`，`WebAssembly.compile/instantiate` 会被拒绝（来源：MDN `script-src`、CSP3 §4.5.1，见附录 B）。
- 后果：
  1. 在 `vite dev` 下做 WASM PoC 会**假阳性通过**；打包后（`tauri build`）才暴露。
  2. 修复必须放松 CSP。若 WKWebView 不支持 `'wasm-unsafe-eval'`（**未验证**），只能加 `'unsafe-eval'`，安全放松范围更大。
- 因此：**任何 WASM 方案的第一步不是写 Rust，而是在打包后的 WKWebView 里验证 CSP 关键字、SIMD、线程（SAB）是否可用**。这一步不通过，后续都无意义。

## 4. 逐场景评估

> 说明：以下"成本"均为机制推断（D 级），没有真机帧级采样；不得当作已测量结论。

### H1 思维导图文本测量与布局

**机制与证据**

- 布局入口：`layoutMindmap`（`src/features/mindmap/utils/layout.ts:49-107`）只做树遍历与坐标计算；`sizeTopic` 对每个主题调用 `measureTopic`（`layout.ts:109-127`）。
- 测量实现：`measureTopic` 先查缓存（`src/features/mindmap/utils/measure.ts:24-26, 29-69`）；未命中时 `wrapText` 按 token 逐个调用 `measureText`（`measure.ts:155-171`），而 `measureText` 每次都会设置隐藏 `span` 的 `textContent` 再读 `offsetWidth`（`measure.ts:132-142`）。
- 布局只在内容变化时重算：`useMindmapViewState` 用 `useMemo(() => layoutMindmap(history.content), [history.content])`（`src/features/mindmap/hooks/useMindmapViewState.ts:84`）。

**为什么不能下移 Rust**

- 宽度必须与 WKWebView 实际排版（系统字体 PingFang SC、字重、字距、断行）一致；Rust 拿不到 WebView 的字体整形结果。
- 若在 Rust/WASM 里用嵌入式字体 + shaping 复现，会引入：中文字体体积（数 MB～十几 MB）、PingFang 不可再分发、与 CSS 渲染不一致导致"测量宽度刚好、渲染却折行"的溢出风险（`measure.ts:1-7` 已记录过同类真机问题）。

**WASM 判定：不适合**

- 成本主体是**每次 `offsetWidth` 的强制同步布局**（机制事实），不是宽度算术；WASM 只能接管后者，收益接近 0。
- 冷启动首次布局（例如数千节点、每个主题多个 token）是线性放大的强制布局，WASM 无法消除。

**更优解（纯 JS，按收益排序）**

1. 用 `CanvasRenderingContext2D.measureText` 替代隐藏 span：不触发布局，字体串取自 `getComputedStyle`，与渲染同源；仍可保留缓存。
2. 不再逐 token 测量：先测整行/整段宽度，断行用二分或按字符宽度累积；或一次性写入多个 span 后批量读宽度（单次布局）。
3. 缓存键不要拼全文（当前键包含 `topic.text`，大图下键本身也变长）；用文本哈希 + 元信息版本。
4. 只对变化节点重测（当前已有缓存，但布局仍全树遍历；遍历本身便宜，可保持）。
5. Worker/OffscreenCanvas 可进一步移到后台，但 WKWebView 的 Worker 内 `measureText`/OffscreenCanvas 支持需真机验证（**未验证**），且字体可得性未确认。

**验证方式**：在生产构建里对"打开 1k/5k 节点导图 + 首次布局 + 单节点编辑"打 `performance.mark`，比较 p50/p95；目标是把首屏布局压到一帧内。数值目标需实际测量后确定。

### H2 编辑器每次 docChanged 的 TOC/大纲（第三方扩展的隐藏 O(doc)）

**机制与证据**

- `TableOfContents` 扩展在每个 `docChanged` 事务上：
  - `appendTransaction` 遍历 **整篇文档所有节点** 检查/补 `data-toc-id`（`node_modules/@tiptap/extension-table-of-contents/dist/index.js:9-31`）；
  - `onTransaction` 直接调用 `setTocData`（同文件 `:232-243`），后者再次遍历文档、并对每个标题执行 `editor.view.domAtPos(...)` 与读取 `offsetTop`（同文件 `:95-121`）。
- 项目侧的 `publishOutline` 只做了"标题没变就不换引用"，避免订阅方重渲染（`src/features/editor/editorOutline.ts:52-60`）；**它无法阻止上面的计算与布局读取**，因为那是第三方扩展在回调之前做的。
- 对照：`CharacterCount` 的 per-transaction 计数只在配置了 `limit` 时才发生；本项目未配置 limit（`node_modules/@tiptap/extensions/dist/index.js:48-55`，配置见 `src/features/editor/extensions/editorExtensions.ts:140-142`），所以每键成本不来自它。

**为什么不能下移 Rust**

- 文档在 ProseMirror 内存对象图里；每个按键都序列化给 Rust 再回来，成本高于遍历本身。
- `domAtPos`/`offsetTop` 是浏览器几何，Rust 完全拿不到。

**WASM 判定：不适合** —— 对象图 + DOM 双重绑定，WASM 两条都过不去。

**更优解（纯 JS/配置层）**

1. 把 TOC 更新从"每个事务"改为"仅在标题结构可能变化时 + 空闲时"：过滤事务（例如仅当 `docChanged` 且变更集涉及 heading/段落层级时）或节流到 `requestIdleCallback`/rAF 尾。
2. 若扩展不提供开关：评估替换为自写的轻量 outline 插件（只在标题增删/文本变化时更新，输出位置信息时避免逐标题读布局）。
3. 大纲浮层只在打开时计算"当前激活项"，不要每次按键都算。
4. 任何改动都要补长文档测试（如 5 万字 + 200 标题）与打字延迟验收。

**验证方式**：在长文档里连续输入 200 字，比较修改前后主线程 long task 数、按键到下一帧的 p95（口径参考 2026-10-27 报告 §9）。

### H3 字数统计与崩溃草稿

**机制与证据**

- 字数：`syncLiveCount` 250ms 合帧，调用 `current.storage.characterCount.characters()`（`src/features/editor/components/DocEditor.tsx:190-207`）——每次仍遍历全文。
- 崩溃草稿：编辑后 2s 定时器执行 `saveDraft(draftNodeId, current.getJSON())`（`DocEditor.tsx:725-737`）；`saveDraft` 做 `JSON.stringify` 后同步写 `localStorage`（`src/features/editor/utils/documentDraft.ts:17-23`）。
- 自动保存：1s 防抖 + 最长 8s，拿锁后才 `getJSON()` 并 `invoke("doc_save"...)`（`src/features/editor/hooks/useDocumentPersistence.ts:17-21, 127-142`）。字数由 Rust 保存结果回传，前端不重复算。

**为什么不能下移 Rust**

- 实时字数必须基于当前内存中的文档；每次按键发给 Rust 不现实（且序列化更贵）。
- 草稿可以改成后端命令，但那就不是"前端性能点"了；问题本质是"对象图 → 字符串"的序列化成本 + 同步存储。

**WASM 判定：不适合** —— `JSON.stringify` 在 JSC 里是原生实现；把对象图搬进 WASM 需要先遍历/复制，通常更慢；WASM 压缩（zstd 等）只能减少写入字节，不能减少序列化遍历，且 localStorage 同步写仍是主线程。

**更优解（纯 JS/调度层）**

1. 字数改为事务增量维护（记录上一次计数 + 本次事务的文本增量），避免每 250ms 全量遍历；或仅在空闲时全量校准。
2. 草稿写入改到 `requestIdleCallback`/长空闲，或只在"停止输入 N 秒"后写；避免与打字同帧。
3. 评估 `IndexedDB`（结构化克隆，免 `stringify`）或后端草稿命令；先量长文档 `stringify` 的真实耗时再决定。
4. 草稿体积设上限（当前已有 try/catch 兜底，但没有体积策略）。

**验证方式**：10 万字文档连续输入，记录 `getJSON+stringify` 的单次耗时与写入期间掉帧；目标是不出现在按键后的同一帧。

### H4 预览/SVG 光栅化（导图/画板 → PNG）

**机制与证据**

- 导图导出：`renderMindmapSvg` 复用同一套 `layoutMindmap`（`src/features/mindmap/utils/exportGraphics.ts:33-39`），再用 `DOMParser` + `Image` + `canvas.drawImage` + `canvas.toBlob` 光栅化（`exportGraphics.ts:217-243`）。
- 画板预览：`renderBoardPng` 直接调用 Excalidraw 的 `exportToBlob`（`src/features/board/utils/exportScene.ts:49-62`）。
- 触发时机：源保存静止 1200ms 后调度，单飞、按节点去重（`src/features/editor/utils/nodePreview.ts:26-32, 49-56`）。

**为什么不能下移 Rust**

- 光栅化依赖浏览器对 SVG/CSS/字体的渲染（导图 SVG 里含文本、圆角、图片）；Excalidraw 的渲染器是第三方浏览器实现，无法在 Rust 复刻。
- 若把 SVG 交给后端 resvg：需要后端字体与前端一致，才能保证导出与画布一致；中文/手写字体涉及再分发许可，且属于"导出保真"问题，不是纯性能问题。

**WASM 判定：不适合**

- `resvg-wasm` 能替掉 `DOMParser/Image/canvas` 的一部分，但仍需嵌入字体才渲染文本；字体不一致会改变导出结果。收益是"把一次后台导出搬进另一个后台"，不解决交互帧。
- PNG 编码本身由 Canvas 原生完成，不是 JS 热点。

**更优解**

1. 保持在保存静止后导出（现状），并确保导出期间不阻塞用户可见交互（可用 `scheduler.postTask`/空闲调度，需确认 WKWebView 支持）。
2. 若导出延迟成为真实问题（大图/大画板），优先评估**后端 resvg + 受控字体**，作为"导出"专用路径；不要在前端再维护一套渲染器。
3. 控制预览尺寸（已有 1600px 上限），避免超大画布。

### H5 文件树装配/排序/复用

**机制与证据**：`buildTree` 按 `parentId` 归组、排序，并自底向上复用旧 `TreeNode` 实例以避免整树重渲染（`src/features/workspace/utils/tree.ts:13-75`）；B2 已把树行/侧栏做成 memo 边界（2026-10-27 报告）。

**WASM 判定：不适合** —— 纯 JS 对象数组，进出 WASM 需要复制；收益上限是排序常数，低于 IPC/编解码成本。

**更优解**：保持现状；若未来出现万级节点，优先把"排序 + 子树统计"下移 Rust 并只回传受影响子树，而不是 WASM。

---

### H6 指针热路径（块手柄/块拖拽/图片缩放）

**机制与证据**：块手柄在 `mousemove` 里 O(块数) 扫描 `getBoundingClientRect`；块拖拽每帧 O(块数)；文件树 `dragover` 曾每次 `setState`；图片缩放曾在 `pointermove` 逐事件 `setState`（2026-10-27 报告 B4）。B4 已做矩形缓存 + rAF 合帧 + bail-out（`docs/更新日志/2026-10-27-更新内容-022.md:10`）。

**WASM 判定：不适合** —— 成本是 DOM 几何读取与 React 提交，WASM 两者都碰不到。

**更优解**：继续沿 B4 方向（缓存失效策略、只读一次布局、CSS 变量直写、指针事件合帧）；用真机复测确认 B4 的实际收益（当前未测出提升的记录见项目记忆，需按同构建同场景复测）。

---

### H7 渲染/合成/重型视图挂载

**机制与证据**：`backdrop-filter` 大面积模糊、顶层状态牵动整树渲染、标签切换 `mode="wait"` 串行挂载重型编辑器（2026-10-27 报告 B1–B3）。这些是合成/React 提交/挂载成本，与算术无关。

**WASM 判定：无关** —— 不存在"用 WASM 渲染 React 组件"的合理路径；Canvas 重写编辑器/画板也不成立（会丢掉 Tiptap/Excalidraw 的编辑能力）。

**更优解**：按既有 P1 清单执行（去/降模糊、渲染边界、标签保活/延迟动画），并做真机采样。

---

### H8 语法高亮（lowlight）

**机制与证据**：`CodeBlockLowlight.configure({ lowlight })`，使用 `common` 语法集（`src/features/editor/extensions/editorExtensions.ts:37, 119`）。输入是代码块文本，输出 HTML。

**WASM 判定：暂不适合** —— 纯字符串处理理论上可 WASM（tree-sitter）或下移 Rust（syntect），但：编辑器需要按事务实时高亮，下移 Rust 有 IPC 往返；当前代码块规模未知，没有任何测量表明它是热点；tree-sitter wasm 的包体与初始化成本远高于 highlight.js。

**更优解**：先测量大代码块（如 5000 行）首次渲染与编辑延迟；真有瓶颈时优先"仅高亮视口内 + 增量高亮"，再考虑原生/ WASM。

---

### H9 已下移 Rust 的反例（说明架构方向是对的）

- 搜索：FTS5 trigram + 1–2 字 LIKE 回退 + 最近节点（`src-tauri/src/services/search_service.rs:1-40`、`src-tauri/src/repositories/search_repository.rs:146-179`）。
- 附件预览：文本/Markdown/Word 在 Rust 解析为块 JSON，带 512KB/8MB 上限、400 块上限、16 容量有界预计算队列（`src-tauri/src/services/attachment_preview_service.rs:27-40`）。
- 导入导出：`pulldown-cmark`、`docx-rs`、`office_oxide`、`printpdf`、`pdf-inspector`（`Cargo.toml:35-39,48`）。
- 图像处理：`image` crate（`Cargo.toml:39`）；前端上传走 raw bytes，不在 JS 里解码/缩放（`src/api/attachment.ts:133-139`）。

**结论**：同类需求继续走 Rust；WASM SQLite、WASM 解析器只会带来功能缺口与性能回退。

---

### H10 未来可能真正适合 WASM 的候选（均需先评估原生方案）

| 候选 | 为什么可能适合 | 先评估 | WASM 仅在何时考虑 |
|---|---|---|---|
| 应用内 PDF 页面渲染 | 浏览器上下文渲染，排版复杂 | WKWebView/PDFKit 原生预览、后端渲染 | 产品要求"应用内、跨平台一致、可控渲染"且原生不可行 |
| 本地语义检索/嵌入推理 | 纯数值矩阵运算，TypedArray 常驻 | Rust `ort`/`candle` 后端推理 | 必须离线且必须在 WebView 内、不能起后端任务 |
| 图像像素级处理（缩略图/滤镜） | 天然按字节处理 | Rust `image` + raw bytes IPC | 必须逐帧/交互式处理，IPC 往返成瓶颈 |
| 协同编辑 CRDT 重放 | 纯数据结构 | Yjs（JS）通常够用 | 实测协同规模导致 JS 卡顿 |

## 5. 引入 WASM 的架构成本（本项目特有）

| 成本项 | 事实/说明 | 影响 |
|---|---|---|
| **CSP** | 生产 `script-src 'self'`（`src-tauri/tauri.conf.json:36-39`）；CSP3 会拦截 Wasm 编译 | 必须加 `'wasm-unsafe-eval'` 或 `'unsafe-eval'`；前者在 WKWebView 支持情况**未验证**，后者安全放松更大 |
| **dev/prod 差异** | `devCsp: null` | WASM PoC 在 dev 通过不代表打包可用；必须真机打包验证 |
| **线程** | WASM 线程需 SharedArrayBuffer + 跨源隔离；Tauri 自定义协议下是否可行**未验证** | 很可能只能单线程，丧失对原生 Rust 的最大劣势 |
| **SIMD** | 需要 WebKit 版本支持（**未验证具体基线**） | 数值内核的加速幅度不确定 |
| **构建链** | wasm-pack/wasm-bindgen、wasm-opt、Vite 资产、TS 类型、CI | 新增一套构建与产物校验；`scripts/check-licenses.mjs` 需覆盖 wasm 依赖 |
| **包体/启动** | wasm 模块 + 字体（若做文本）可能数 MB | 主 chunk 已约 2.1MB、`dist` 约 10MB；需设体积预算 |
| **双实现** | AGENTS.md §7 要求同一逻辑单一权威实现 | 需把算法抽成共享 crate 同时编 native 与 wasm32；否则维护两套 |
| **调试/可观测** | WASM 栈帧、内存、panic 映射都更难 | 排障成本上升；现有 `interactionProbe` 只能测边界 |
| **安全/供应链** | 放松 CSP + 引入 wasm 二进制 | 需固定来源、校验哈希、许可证门禁 |
| **许可** | wasm-bindgen（MIT/Apache）、resvg（MPL-2.0，弱 copyleft 警告）、pdf.js（Apache-2.0）、onnxruntime（MIT） | 按项目门禁，MPL 只警告；仍需逐项确认版本与分发方式 |

## 6. 建议与优先级

### 6.1 现在（P0）：不引入 WASM，先把"假热点"变成"可测量"

1. **记录决策**：本报告作为"暂不引入 WASM"的依据；后续只有在 §6.3 条件满足时重新立项。
2. **H1 测宽改造**：隐藏 span → Canvas `measureText` + 整行断行 + 缓存键优化；改造后用 1k/5k 节点导图做生产构建采样。
3. **H2 TOC 降频**：避免每个 docChanged 都全量遍历 + 逐标题读布局；用长文档（5 万字/200 标题）验收按键延迟。
4. **H3 长文档测量**：先量 `getJSON+stringify` 与 `characters()` 的真实耗时，再决定增量计数/空闲草稿/IndexedDB/后端草稿。
5. **复测口径**：严格按 2026-10-27 报告 §9（生产前端构建、隔离 `STARRIS_HOME`、同场景多次采样、A/B 注入），不要用 dev + StrictMode 下结论。

### 6.2 之后（P1/P2）

- H4：预览导出保持"保存后空闲触发"；若导出延迟成为用户可感问题，评估后端 resvg（受控字体）。
- H6：验证 B4 的实际收益；继续用缓存 + rAF + CSS 变量，不上 WASM。
- H7：按既有 P1 清单处理模糊/渲染边界/标签挂载；这是当前最可能影响"丝滑感"的部分。
- H8：只有实测大代码块卡顿后才考虑增量高亮。

### 6.3 WASM 准入清单（未来重新评估时逐条打勾）

- [ ] C1 数据常驻 TypedArray，跨边界调用只传索引/标量；
- [ ] C2 已测量：单次 > 数 ms 或每帧必需，且 JS/Worker 达不到帧预算；
- [ ] C3 该计算必须留在 WebView（DOM/字体/Canvas/交互帧），原生 Rust 无法替代或往返更贵；
- [ ] C4 同构建 A/B 显示端到端（含拷贝）≥ 2× 收益，且收益 > 包体/CSP/维护成本；
- [ ] CSP 已在**打包后的 WKWebView** 验证（`wasm-unsafe-eval`/`unsafe-eval`、SIMD、线程）；
- [ ] 许可证门禁通过；wasm 产物有哈希与来源记录；
- [ ] 算法抽成共享 crate，native 与 wasm 同一份实现（C5）；
- [ ] 有 JS 回退路径与降级策略；
- [ ] 有可重复的基准脚本与验收阈值。

## 7. 风险与未决问题

1. **WKWebView 行为未实测**：CSP 关键字支持、SIMD 基线、SharedArrayBuffer/跨源隔离、Worker 内字体测量/OffscreenCanvas——全部标注为未验证；任何 WASM 方案必须先过这一关。
2. **没有真机数字**：H1/H2/H3 的成本均为机制推断；本报告不宣称任何提升。落地时必须按 2026-10-27 报告 §9 采样。
3. **TOC 属于第三方扩展**：降频/替换需要改第三方行为（MIT），要评估升级维护与回归成本；不得只为性能引入分叉而不记录。
4. **字体许可**：若未来做嵌入式字体测量/导出，必须确认可再分发（PingFang 不可；现有白名单字体有限）。
5. **规模未知**：典型/最大文档字数、文件树节点数、导图节点数未收集；这直接决定 H1/H2/H3 的优先级，需要用户提供或构造测试数据。
6. **"极致优化"的收益顺序**：把 1ms 的计算加速 10 倍只省 0.9ms；而一次强制布局或一次整树 React 提交可能是数 ms 到数十 ms。先消布局/提交，再谈指令级加速。
