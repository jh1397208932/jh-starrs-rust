# 任务-001 计划：允许同名附件上传（v5 → v6）

- 日期：2026-10-23
- 关联需求：
  - `docs/需求文档/2026-10-22-需求文档-附件对象存储.md` §3.2 逻辑元数据、§8 第 6/11 条
  - `docs/需求文档/2026-10-22-需求文档-文档图片与附件块.md` §7 第 12 条
- 前序任务：`docs/开发任务清单/2026-10-22-任务-005/`（对象存储）、`2026-10-22-任务-006/`（图片/附件块）

## 1. 问题

真机反馈：连续粘贴两张都叫 `image.png` 的剪贴板图片，第二次报

```text
上传完成 0 个，1 个失败：image.png：该目录下已存在同名附件
```

根因是任务-005 把「同目录同名唯一」当成了存储层规则，落在三处：

| 位置 | 内容 |
| --- | --- |
| `db/workspace.rs` v5 迁移 | `CREATE UNIQUE INDEX uq_attachment_active_path ON attachment(logical_path, name) WHERE status='active'` |
| `services/attachment_service.rs` `upload_staged` | 插入前 `find_active_by_path` 预检 → `AppError::conflict` |
| `services/attachment_service.rs` `update` | 改名/移动前同样的预检 |
| `services/attachment_service.rs` `map_attachment_insert_error` | 把约束冲突再翻译成同一句话 |

这条规则与内容寻址模型自相矛盾：附件身份是 `id`，去重靠 BLAKE3，物理路径由哈希决定，文件名只是展示元数据。两张不同的截图都叫 `image.png` 是常态，不该互相排斥。

## 2. 目标与范围

目标：不管文件名是什么，上传都必须成功并返回对应附件 id；重名不影响列表、预览、下载、删除与去重。

范围内：

1. v5 → v6 迁移：撤下唯一索引，改建目录检索用的非唯一索引。
2. 服务层：删除上传与改名两处同名预检，删除约束翻译函数。
3. 仓储层：删除唯一调用方已不存在的 `find_active_by_path`。
4. 测试：先写失败用例，再实现；迁移测试补「唯一索引确实没了」的直插验证。
5. 文档：需求、数据库设计与迁移、单元测试、更新日志、记忆。

范围外：不改前端（错误文案由后端消息驱动，规则放开后自然不再出现）；不改物理布局与哈希策略；不引入自动改名（`image (1).png`）——那是把展示层的歧义推给用户。

## 3. 方案与取舍

| 方案 | 说明 | 取舍 |
| --- | --- | --- |
| 撤下唯一约束（选定） | 名称降级为纯展示元数据，身份只认 id | 与内容寻址一致；列表里同名条目靠 id/时间区分，前端本就按 `item.id` 做 key |
| 冲突时自动改名 | 上传时补 `(1)`、`(2)` | 用户看到的文件名与真实文件不符，且仍要处理并发撞名；否决 |
| 只放开上传、保留改名冲突 | 上传可重名，重命名仍拒绝 | 同一条规则两处口径不一致，等于保留错误模型；否决 |

历史迁移不改写：`MIGRATION_V4_TO_V5` 原样保留（含它建的唯一索引），由 `MIGRATION_V5_TO_V6` 负责 `DROP INDEX`。空库路径按 v4→v5→v6 连跑，终态一致。

## 4. 步骤

1. 写失败测试：`attachment_allows_duplicate_names_and_returns_distinct_ids`；同时把 `attachment_rename_and_move_only_change_metadata` 中「重名必须冲突」的断言翻正。
2. `SCHEMA_VERSION` 5 → 6，新增 `MIGRATION_V5_TO_V6`，接入 `migrate()` 两条分支。
3. 迁移测试补：版本停在 6、`uq_attachment_active_path` 不在、`idx_attachment_active_path` 在、直插两条同名活跃行成功。
4. 删除服务层两处预检与 `map_attachment_insert_error`，删除仓储 `find_active_by_path`。
5. 门禁：`cargo fmt --check`、`cargo clippy --all-targets`、`cargo test`、`npm run check`、`npm run typecheck`、`npm run build`。
6. 同步文档。

## 5. 风险

- 已发布过的老库依赖「同名唯一」做定位？全仓检索确认 `find_active_by_path` 只服务于这两处预检，无其他调用方；前端列表/编辑器一律按 `id` 索引。
- 同名条目在设置页列表里视觉上重复——属预期，行内已展示目录/大小/时间，且 key 用 id。
- 迁移只 `DROP INDEX`，不动数据，可回退性由 SQLite 文件本身保证；不重建表。
