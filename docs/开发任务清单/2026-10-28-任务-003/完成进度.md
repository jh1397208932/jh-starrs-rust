## 第二轮 MCP / 维护审查（18:05–18:30，纯白盒）

`mcp_host.rs` 与 `mcp.rs` 这一遍读下来没有新问题：端口重试、锁中毒取回内部值、批量请求显式回 -32600（不回 202）、令牌缺失写进可见错误、常量时间比较、4 MiB 请求体上限、60 秒超时只结束 HTTP 等待不谎报取消。工具状态只有 `ok / pending_review / denied` 三种，失败一律走 JSON-RPC error 信封，所以 `isError` 只对 `denied` 成立是对的。

审出并已修的三个：

1. **入队后没人认领的待审项永远不露面**（`AiReviewLayer` 只订阅事件）。MCP 在应用未开 / 刚重启 / 工作区尚未挂载确认层时入队，事件早已丢失，客户端只看到「已进入待审区」。现在打开工作区时按 `created_at` 从旧到新重建最多 10 条对比（`listAiInbox("pending")` + 之前无人调用的 `ai_review_preview`），读取失败保持现状。**代价**：确认弹窗会在打开工作区时主动出现，所以 `dismissStrayPanels` 同步把「确认执行 / 稍后处理」也判作模态残留，避免残留弹窗卡死后续用例。
2. **审批写失败后可能把状态写进别的库**（`ai_service.rs` approve 的 Err 分支）。认领与执行之间用户切了工作区或关掉工作区，原实现直接拿当前连接 `fail_inbox`：要么写进无关库，要么因为「无活动工作区」报错、记录卡在已认领状态。现在与成功分支一样先核对工作区身份，不匹配只记日志。
3. **「立即清理」会重写仍在使用对象的 pack 文件**（`compact_pack_if_needed` 搬数据 + 改 `attachment_blob` 偏移），而界面文案承诺「正在使用的文档、画板、思维导图与附件不会被改动」。现在拆成两条路径：`run`（后台看门狗 / 工作区补跑，保留 pack 重写）与 `run_manual`（`attachment_maintenance` 命令走这条，只做无用数据回收），其余判据两条完全一致。

审出但**本轮没改**的两处，需要用户拍板：

- **确认窗的对比是入队那一刻算的**。`doc_replace_range` / `doc_update` 载荷里只有下标；若用户在待审期间自己改了同一篇文档，点「确认执行」落的库可能不是他看到的那份对比。修法要在 `ai_inbox` 存一份入队时的快照或版本号，`approve` 前重算并拒绝过期确认（SQLite 加 CHECK 取值需重建表 → v16→v17 迁移），不适合在真机窗口前动。
- **认领 = 先写 `status='approved'` 再执行**。这是防双击重复写入的做法，但进程在「已认领、未执行完」之间被杀，记录会显示已批准而实际没写。要彻底解决需要新增一个非终态取值（同样落在三份 `ai_inbox` DDL：基线 `SCHEMA`、`MIGRATION_V8_TO_V9`、`REPAIR_AI_TABLES`，改一处漏两处就是第二份事实）。
