# 需求文档 · MCP 托管到客户端（2026-10-27）

## 1. 背景与目标

当前 `starris-mcp` 是一个独立 stdio 程序：它能脱离桌面端单独启动、自己打开工作区数据库、自己执行初始化与权限判定。这与产品定位不符——MCP 应是**客户端启动后携带的能力**，生命周期、数据会话与权限上下文都属于正在运行的星屿客户端。

目标：

1. 客户端启动时托管 MCP 服务，关闭客户端即停止；不再提供可独立运行的服务程序。
2. Agent 通过本机 HTTP 端点 + 令牌连接，工具调用复用客户端当前的 `AppState`（同一工作区连接、同一权限与待审区）。
3. 保留现有 21 个工具、三作用域权限（只读/需人工确认/可编辑）、待审区与审计。
4. 设置 → AI 协作 展示服务状态、端点、令牌与开关。

## 2. 范围

做：

- 客户端内置 HTTP JSON-RPC 服务：`POST /mcp`（initialize / ping / tools/list / tools/call），`GET /health`。
- 仅监听 `127.0.0.1`，固定默认端口 `47821`（`STARRIS_MCP_PORT` 可覆盖）；启动失败在设置中显示原因。
- Bearer 令牌鉴权；令牌首次启动生成并存入全局库，可在设置中查看/复制/重置。
- 开关：关闭后停止监听；再次开启立即重启。
- 删除 `src/bin/starris_mcp.rs`、stdio 循环与 headless 启动分支。
- 设置页新增 MCP 区块（独立子组件，避免超行数上限）。
- 真机 E2E 新增 `28-mcp-host` 用例：无令牌 401、initialize、tools/list、tools/call、关闭开关后不可用。

不做（首版）：

- SSE 事件流、会话恢复、多租户/多端口、远程监听、mTLS。
- 端口编辑 UI（环境变量覆盖即可）。

## 3. 使用场景

1. 用户打开星屿 → 设置 → AI 协作 看到「MCP 服务：运行中」，复制端点与令牌。
2. 在 agent 的 MCP 配置里填 `url: http://127.0.0.1:47821/mcp` 与 `Authorization: Bearer <token>`。
3. Agent 调用 `kb_list` / `doc_read` / `doc_create` 等；写入按权限直写或进入待审区。
4. 用户退出星屿 → 端点不可达；再次启动后沿用同一令牌与端口。

## 4. 安全与数据

- 绑定 loopback，不监听外部网卡。
- 令牌 32+ 字符随机串，全局库 `settings.mcp.token`；日志与错误提示不得输出令牌。
- 无令牌/错误令牌：HTTP 401，JSON-RPC 错误体，不执行任何工具。
- 权限与待审逻辑不变，仍由 `ai_service` 统一判定。
- 请求体限制 4 MiB，超限 413；非 JSON 400。

## 5. 验收标准

1. 客户端启动后 `GET /health` 返回 ok；无令牌 `POST /mcp` 返回 401。
2. 正确令牌下 `initialize` 返回 `serverInfo.name = "starris-mcp"`，`tools/list` ≥ 21 且 schema 完整，`tools/call kb_list` 返回当前工作区数据。
3. 关闭 MCP 开关后端口拒绝连接；重新开启恢复。
4. 关闭客户端后端口不可用（能力随客户端启停）。
5. 仓库内不存在可独立运行的 MCP 服务二进制；`cargo run` 只有桌面端一个目标。
6. 全量真机 E2E（29 用例）通过；Rust 测试、clippy、fmt、前端 build/check 全绿。
