# 更新日志：允许同名附件上传（存储 v6）

- 日期：2026-10-23
- 关联需求：`docs/需求文档/2026-10-22-需求文档-附件对象存储.md` §3.2/§8、`docs/需求文档/2026-10-22-需求文档-文档图片与附件块.md` §7 第 12 条
- 关联任务：`docs/开发任务清单/2026-10-23-任务-001/`

## 问题

真机连续粘贴两张都叫 `image.png` 的剪贴板图片，第二次报「上传完成 0 个，1 个失败：image.png：该目录下已存在同名附件」。

根因不是校验过严，而是模型自相矛盾：附件存储是内容寻址的——身份是 `id`、去重靠 BLAKE3、物理路径由哈希决定，文件名只是展示元数据；但任务-005 又把「同目录同名唯一」写成了部分唯一索引，并在服务层加了两道同样的预检。两张不同的截图都叫 `image.png` 是常态，被这条规则互相排斥后，用户看到的就是"传不上去"。

## 变更

1. **v5 → v6 迁移**（`db/workspace.rs`）：`DROP INDEX uq_attachment_active_path`，改建非唯一的 `idx_attachment_active_path(logical_path, name) WHERE status='active'` 供目录检索。历史迁移 `MIGRATION_V4_TO_V5` 原样保留，由 v6 负责撤下；空库按 v4→v5→v6 连跑，终态一致。只删索引，不动数据。
2. **服务层去约束**（`services/attachment_service.rs`）：删除 `upload_staged` 与 `update` 里两处 `find_active_by_path` 预检，删除把约束冲突翻译成那句话的 `map_attachment_insert_error`。改名/移动同样不再因重名被拒。
3. **仓储层清理**（`repositories/attachment_repository.rs`）：删除失去全部调用方的 `find_active_by_path`。
4. **前端零改动**：上传返回仍是 `AttachmentDto`；编辑器与设置页一律按 `id` 索引，同名不影响 React key、预览、下载与删除。

## 用户可见变化

- 同名文件（不同内容）可以反复上传，每次都拿到自己的附件 id 并正常回显。
- 同名且同内容时仍只占一份物理空间：`unique_objects` 不增，逻辑行各自独立。
- 设置页附件列表可能出现同名多行，靠目录/大小/时间区分——这是预期行为。

## 验证

- 先写失败测试：改前运行即复现用户那条错误消息；改后 `cargo test` **58 passed / 0 failed**（57→58）。
- 新用例断言：两个同名不同内容 → id 与哈希均不同、列表 2 条；再加同名同内容 → `active_count=3`、`unique_objects=2`；跨目录同名互不影响；改名到已有同名目录后仍可上传同名。
- 迁移测试补强：版本停在 6、唯一索引不在、非唯一索引在，并在迁移后的库直插两条同目录同名活跃行，证明约束确实没了而非被别处兜住。
- 门禁：`cargo fmt --check` 通过、`cargo clippy --all-targets` 无项目警告、`npm run check`/`typecheck`/`build` 通过（许可证门禁通过，9 项 MPL-2.0 弱 copyleft 警告）。
