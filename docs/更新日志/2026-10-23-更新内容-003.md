## 背景

`ref_count` 是冗余字段：物理对象该不该存在，只用看"还有没有活跃 `attachment` 行引用这个哈希"，一条走 `idx_attachment_hash` 的 COUNT 就能算出来。存一列维护它，等于给同一个事实维护第二份真相——写入路径漏一次就永久漂移，而且读的时候还得相信它。

## 变更

1. **v6 → v7 迁移**（`db/workspace.rs`）：重建 `attachment_blob` 去掉 `ref_count`，`INSERT ... SELECT` 搬运全部行，重建 `idx_attachment_blob_pack`。列上原本带 `CHECK (ref_count >= 0)`，SQLite 不允许带约束的列直接 `DROP COLUMN`，故按官方做法重建表。
2. **仓储**（`attachment_repository.rs`）：删除 `increment_ref` / `decrement_ref`；新增 `count_active_references(hash)` 作为唯一判据；`max_indexed_end` / `live_bytes_in_pack` / `list_live_blobs_in_pack` / `move_blob_to_pack` / 统计里的 `ref_count > 0` 过滤全部去掉——blob 行只在被引用期间存在，"存在即有引用"本身就是不变量。
3. **服务**（`attachment_service.rs`）：上传命中已有 blob 时不再 +1，直接跳过物理写入并插入逻辑记录；删除时先 `mark_deleted`，再数活跃引用，为 0 才删 blob 行与真实文件。
4. **模型**：`AttachmentBlobRow` 去掉 `ref_count` 字段；注释写明判据在 `count_active_references`。
5. IPC 契约不变：`AttachmentDeleteResult.remaining_references` 仍在，值是删除后现算的活跃引用数（前端"内容仍被其他附件引用"的提示继续有效）。

## 用户可见变化

无。上传、回显、下载、删除的行为与 v6 完全一致；本次只是把冗余状态删掉。

## 已知限制

- `count_active_references` 数的是逻辑记录数，不是文档节点引用数——这一点与 v6 相同，没有变化；要覆盖文档侧引用需另做「文档节点 → 附件」登记。
- 真实 Tauri 下 v6→v7 自动迁移未实测：需重启 `npm run tauri dev`，确认日志里的迁移版本与旧附件仍可读、可下载。
- 迁移会重建 `attachment_blob`（数据搬运，非破坏性），但老库若体量很大，首次打开会有一次短时的写放大；本机数据量级下可忽略。
