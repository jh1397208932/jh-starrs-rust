## 组件库（画板右侧）

- **缩略图不再逐张等待**：生成器从"每张后固定让出 16ms"改为按帧时间预算（8ms）批量生成。真机实测 `perf.library previews=206 total=190ms`（≈0.9ms/张）；旧实现仅固定等待就是 206×16≈3.3s——"先空图标、等一会才出图"的主因。
- **打开面板即预热**：当前分类优先排队生成，滚动到哪一类都已经有图。
- **生成中显示骨架**：占位从"空图标"换成 shimmer 骨架（尊重 reduced-motion），不再像加载失败。
- **大组件也有预览**：超过 80 图元的组件改为截取前 80 图元生成，不再直接空着。
- **离开视口不再取消任务**：生成结果进缓存，滚回来直接命中。
- **卡片 memo 化**：画板每次保存/状态切换不再连带重渲染 60+ 张卡片。
- **列表缓存**：模块级缓存 + `LIBRARY_CHANGED_EVENT` 过期标记，切换画板标签页不再重复 IPC 拉取并解析 200+ 组件（导入/启停后仍会重新拉取）。
- **回归门**：`40-board` 读取 `perf.library` 汇总，平均单张 ≥8ms 直接判失败。

## 第二轮适配代码清查（2026-10-30 11:00 前）

- **画板保存少一次序列化**：此前把图元数组序列化成字符串写库后，又 `from_str` 解析回 `Value` 供引用同步使用。现在直接消费入参数组、过滤掉已删除图元后只序列化一次，写库与引用同步共用同一份值。
- **文档加载不再修复旧数据**：此前 `document_service::load` 会用 `prepare_document` 删空 emoji/空文本、清 null attrs，并通过 `DocLoadResult.normalized` 让前端自动补一次保存。现改为：保存路径仍是唯一规范化入口；加载时若规范化会改动内容，直接返回“文档内容不符合当前格式，请删除该文档后重新创建”，不修复、不回写；删除 `normalized` DTO 字段与前端补保存分支。集成测试改为 `document_load_rejects_legacy_dirty_content`。
- **打开文档不再重复规范化**：加载路径改用新增的 `validate_document`（只校验、不构造），不再为整篇正文建规范化副本、也不再逐块序列化算哈希；`prepare_document` 仍只在保存时执行。新增等价性用例 `validate_document_agrees_with_prepare_changed`（17 组正反例，接受时必须与规范化输出逐字节相同）；顺带修正 `attrs: {}` 未被计入 `changed` 的不一致。
- **全局库单一 schema**：见上节；新增三条后端用例（空库建表幂等 / 旧版本拒绝 / 有表无版本拒绝）。
- **导图连线值域收窄**：`LayoutEdge.sourceHandle/targetHandle` 从 `string` 收窄为 `ConnectorSide` 联合类型；删除 `normalizeSide` 的 `top/bottom` 别名与“未知回落 right”，布局只产出 `left/right/up/down`，误写会在编译期报错。
- **画板图片加载**：整块画板复用同一个只读连接（此前每张图各开一次工作区连接），base64 直接编码进带 `data:` 前缀的字符串（省掉 `format!` 的整段复制），新增 `perf.board` debug 日志记录张数/字节/耗时。data URL 仍内联——Excalidraw `BinaryFileData.dataURL` 必需。
- **导入附件去重改索引点查**：`unique_attachment_name` 不再为每个导入文件拉 200 行附件列表，改为 `attachment(name_exists)` 按 `(logical_path,name)` 索引 EXISTS；300 文件导入 4.35→4.27s（上传/哈希占主导，收益主要是去掉每文件 200 行 DTO 转换）。
- **文档属性改后台生成**：保存路径不再在保存线程为整篇文档生成属性 JSON，改为把规范化正文交给 `starris-doc-meta` 工作线程解析生成；新增等价性用例 `deferred_payload_matches_eager_props`。两项均待下一真机窗口回归。
- **新增大树极限用例**：`20b-tree-large`（300 个 Markdown 作为文件夹导入，判据：子节点数 300、无重复标题、首尾子项可见）。后端同口径由 `importing_300_markdown_files_builds_complete_folder_tree` 覆盖；UI 已在真机通过（定向 3/3，日志“300 个文档，首尾子项均可见”）。

- **帧探针读数**：`VITE_FRAME_PROBE=1` 构建采集（`tmp/perf/20261030T085618`）：画板 59.9fps/p95 20ms、导图 59.8fps/p95 22ms、长文档打字 59.8fps/p95 21ms，`>33ms` 帧均为个位数；随后恢复普通构建。
- **真机回归说明**：全量 35 例跑出 34/35，唯一失败是 30b 的“全库历史快照”断言被 300 文件用例顶高，已改为按文档统计并由定向 `onboarding+20b+30b` **3/3** 复验；随后尝试的统一复跑在 17:07 被用户中断，中断级联的“未运行”不计为失败。
- **新增「无历史数据」守卫**：`scripts/check-no-legacy.mjs` 扫描产品代码中的迁移链、结构自愈、已下线节点类型（4/5）分支、`DocLoadResult.normalized` 修复标记与旧导图版本写入；先剥注释再匹配，并内置正/反自对照。命令 `npm run check:no-legacy`，已接入 `npm run build`；用临时注入的 `MIGRATION_V1` 验证过会失败、删除后恢复通过。
- **组件库导入加数量上限**：此前只限制文件 32 MiB，未限制组件数量；超大库会让侧栏列表与缩略图生成都变成 O(上万)。现在单库最多 2000 个组件，超出返回「请拆分后再导入」；新增用例 `library_import_rejects_too_many_items`。
- **导出不再带已下线节点类型**：删除“表格(4)/流程图(5)”的导出分支与过滤；知识库导出前先校验每个节点类型，未知类型直接报错，不再静默导出元数据 JSON；树清单补上 `mindmap` 类型。`node.type` 的数据库约束同步收窄为 `IN (1,2,3,6,7)`，工作区库 `SCHEMA_VERSION` 升到 **2**（旧库按规则拒绝打开，删除重建）。
- **IPC/导入体积护栏**：预览图 base64 先按长度粗筛再解码（避免为超大载荷分配解码缓冲）；Markdown/文本导入上限 32 MiB、Word 上限 128 MiB（与 PDF 对齐）；单篇文档正文上限 32 MiB（与画板对齐），超限返回可读错误。组件缩略图缓存加 2000 条上限，反复导入/删除组件库不再无限增长。
- **30b 极限用例加“保存确实落库”判据**：连续 10 轮改写后不再只看界面「已保存」（可能是上一轮遗留的文案），而是等待 `node.doc_version` 严格递增，再确认界面状态。
- **编辑器不再每次渲染重设选项**：`useEditor` 的 `editorProps` 原本每渲染新建对象，tiptap 的 `compareOptions` 判定选项变化，于是每次保存状态/字数刷新都跑一遍 `setOptions`。现在按 `aria-label` 文案值记忆化，只有切换语言才换引用（真机验证见任务记录）。
- **文档历史加字节预算**：快照原本只按「单篇 50 份」裁剪，一篇 2 MiB 的正文最多会留下 100 MiB 历史。现在再加「单篇 16 MiB」总字节预算，超出时从最旧开始删、至少保留 1 份；新增用例 `document_history_stays_within_byte_budget`（12 × 2 MiB 快照收敛到预算内）。
- **自动保存补上限**：文档保存原本只有 1s 防抖，连续输入时计时器不断重置，可能长时间不落盘。新增 8s 最长等待（与画板 5s、导图 8s 一致）：持续打字时也会按 ≤8s 间隔保存一次，崩溃最多丢 8s 内容。保存后仍按原逻辑回到「已保存」。
- **保存路径少算一遍 Markdown**：同一次保存里检索索引与后台元数据各生成一次整篇 Markdown；现在只生成一次，两者共用。
- **其余**：导图标记表 `flag`/`star` 注释去掉“兼容 v1 数据”表述（它们是当前 UI 选项）；附件维护的孤儿认领保留为崩溃一致性 GC，注释不再声称处理旧版本数据。
