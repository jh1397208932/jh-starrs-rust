## 本轮经过（含一次回退，如实记录）

对附件全链路逐条核对，结论如下：

| 环节 | 核对结论 |
| --- | --- |
| 暂存 → 流式 BLAKE3 → 命中即不重复写 → 未命中才发布 → big 两级分桶 / small pack | 与设计一致，未改 |
| 暂存文件命名 | 原为 `tmp/<uuid>.part`，**已改**为哈希算完即改名 `tmp/<BLAKE3>.part` |
| 同一文件重复上传返回哪个 id | 曾按"命中即返回已有 id"实现，随后被更正口径**回退**为现状：每次上传都新建记录，共享同一物理对象，靠引用计数决定删除 |

回退后的最终口径（也是本轮真正要固化的东西）：**同一文件重复上传（文件名可以不一样）产生多条记录、多个 id，但真实文件只有一份；每个物理对象带引用计数，引用全部消失才允许删除。** 这套语义本来就在实现里，本轮把它写进需求、并在测试里钉死，避免下次又被"优化"成命中即复用 id。

补充一个事实纠正：磁盘上此前**也没有**出现过用户真实文件名（big 用哈希名、pack 用 pack id、临时文件用 uuid）。改成哈希名带来的是"崩溃残留自描述、可按 blob 表比对回收"，不是"首次不泄露文件名"。

## 变更

1. `services/attachment_store.rs::stage_reader`：写入期用 `tmp/.<uuid>.writing`，完成后 rename 为 `tmp/<BLAKE3>.part`；该名字已存在（并发同内容或崩溃残留）时删掉自己这份采用既有路径——名字由内容决定，两者字节必然一致。
2. `services/attachment_service.rs::upload_staged`：函数头补中文文档注释写明"每次上传一条记录、命中只 `increment_ref`、归零才物理删除"，并注明该口径 2026-10-23 拍板、勿改成命中即返回已有 id。
3. `AttachmentBlockNodeView`：下载忙碌态由按 `attachmentId` 改为按项（`uid ?? attachmentId`）。同一个附件 id 可以在一个块里出现两次（复制/拖动附件块会连带复制 items），旧写法会让两颗按钮一起转圈。
4. 本轮曾加入的 `find_active_by_hash` 与命中早退已删除，不留死代码。

## 已知限制（不是本轮遗漏）

- `ref_count` 数的是**逻辑附件记录数**，不是"有多少个文档节点在引用它"。所以在设置页删掉一条仍被文档引用的附件，那个节点会显示损坏态——这是既有设计（文档侧从不登记引用），要真正安全需要「文档节点 → 附件」引用登记，属另一个需求。
- 编辑器"移除附件项"只改文档 JSON，不删附件，因此重复上传产生的多条记录需要用户在设置页自行清理。
- 崩溃残留 `tmp/<hash>.part` 目前只有命名自描述，没有按 blob 表比对的自动回收。
