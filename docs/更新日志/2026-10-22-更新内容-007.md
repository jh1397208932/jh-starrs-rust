## 背景

用户在真实 Tauri 窗口截图反馈两个缺陷：选中附件块后布局浮条出现在上方图片块上、与附件卡片无关；从访达把文件拖进窗口后没有任何反应。上一轮功能测试只在 Chromium + IPC mock 下完成，浮条几何没有做「与卡片组对齐」的判据，拖放也没有覆盖真实 Tauri 的原生拦截，两处都漏检。

## 修复内容

### 1. 附件块浮条跟随附件组

- 根因：浮条 `left: 50%` 相对 `.attachment-block-shell` 居中，而该外壳是普通块元素、宽度等于整行正文宽度；卡片只有 210px 且靠左，于是浮条停在行中心，看起来属于上一块。图片块不受影响，因为它的 shell 在 flex 容器里会收缩到图片宽度。
- 改法：对齐交给 `.attachment-block`（flex + `justify-content`），卡片形态下 `.attachment-block-shell` 用 `width: fit-content` 收缩到卡片组宽度，长条形态仍 `width: 100%` 铺满正文。
- 用户可见变化：单卡片/多卡片/居中/右对齐/长条五种状态下，浮条横向中心与附件组中心一致（实测偏差 0px）。

### 2. 访达拖入文件接入对象模块

- 根因：`tauri.conf.json` 未设置 `dragDropEnabled`，其默认值 true 让 Tauri 在原生层接管拖放，网页收不到 HTML5 `drop`，`@tiptap/extension-file-handler` 的 `onDrop` 从不触发（与早前官方 DragHandle 在 WKWebView 失效同源）。
- 改法：新增 `src/api/dragDrop.ts` 订阅 `getCurrentWebview().onDragDropEvent`，只处理 `drop`；事件坐标是相对 webview 左上角的物理像素，按 `devicePixelRatio` 换算成视口 CSS 像素。`DocEditor` 在文档打开期间注册监听，落点经新增的 `resolveDropInsertPos` 解析后走既有**路径流式上传**（`uploadPathsAndInsert`，`kind: "auto"`）：图片插成图片块，其余合并为一个附件块。
- 落点判据：正文容器外的拖放返回 `null` 并放弃插入（拖到左侧树/顶栏不会污染当前文档）；容器内命中不到文字位置时退回文档末尾。
- 用户可见变化：从访达拖一个或多个文件到正文即上传并插入，任意大小都走流式（不受粘贴的 64 MiB 字节上限约束）。

## 验证结果

- Chrome 真实 DOM 几何判据：5 种布局状态浮条与附件组中心偏差均为 0；把样式临时退回旧布局后偏差变为 −645px，撤掉后回到 0（证明判据有分辨力）。
- 落点三分支：容器外 `resolvedPos null` 且不插入；落在首段文字内 `resolvedPos 9` 并在该处分裂段落插入图片块；容器内空白处 `resolvedPos == doc.content.size` 追加到末尾。混合拖入 png + txt 得到图片块 + 附件块。
- 门禁：`cargo test` 57 passed / 0 failed、`cargo fmt --check` 通过、`cargo clippy --all-targets` 无项目代码警告；`npm run check` 118 files、`npm run typecheck` 通过、`npm run build` 通过（许可证门禁通过，9 项 MPL-2.0 弱 copyleft 警告）。
- 本轮无 Rust 代码改动；探针页与临时 Vite 已删除。

## 已知问题

- `tauri://drag-drop` 事件本身由 Tauri 原生层发出，Chromium 无法触发；本轮只验证了事件之后的全部链路，**真机拖放需重启 `npm run tauri dev` 复测**。
- 非 1 的 `devicePixelRatio` 下坐标换算未实测；拖放目录、拖放期间的落点高亮未覆盖。
- 截图未能落盘到仓库：Chrome DevTools MCP 的 `filePath` 受其自身 workspace root 限制，写入本仓库目录被拒；本轮以对话内联截图与几何读数作证。
